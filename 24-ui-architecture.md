# Архитектура интерфейса

## Состояние и сообщения

### Держи состояние в одной структуре и меняй его только сообщениями

Если правду о данных хранят и модель, и виджеты, они рано или поздно расходятся: список показывает одно, данные содержат другое. Поэтому всё, что пользователь может изменить, лежит в одной структуре `state`, ввод превращается в сообщение (размеченное объединение из [главы про паттерны](21-patterns.md)), `update` применяет сообщение к `state`, а `view` только читает `state` и показывает. Поток данных односторонний: событие, сообщение, `update`, `state`, `view`. Это же отделяет данные от их показа без отдельных слоёв: логика приложения не знает про окно и проверяется без него.

```c
#include <errno.h>
#include <stdio.h>

typedef struct { char text[16]; bool done; } todo;
typedef struct { todo items[4]; int count; } state;
typedef enum { MSG_ADD, MSG_TOGGLE, MSG_CLEAR_DONE } msg_kind;
typedef struct { msg_kind kind; union { const char *text; int index; }; } msg;

/* update - единственное место записи в state. Возврат: 0, -ENOSPC или -EINVAL. */
static int update(state *s, msg m) {
    switch (m.kind) {
    case MSG_ADD:
        if (s->count == 4) return -ENOSPC;
        snprintf(s->items[s->count].text, sizeof s->items[0].text, "%s", m.text);
        s->items[s->count++].done = false;
        return 0;
    case MSG_TOGGLE:
        if (m.index < 0 || m.index >= s->count) return -EINVAL;
        s->items[m.index].done = !s->items[m.index].done;
        return 0;
    case MSG_CLEAR_DONE: {
        int n = 0;
        for (int i = 0; i < s->count; i++)
            if (!s->items[i].done) s->items[n++] = s->items[i];
        s->count = n;
        return 0;
    }
    }
    return -EINVAL;
}

static void view(const state *s) {
    printf("%d:", s->count);
    for (int i = 0; i < s->count; i++) printf(" %c%s", s->items[i].done ? '+' : '-', s->items[i].text);
    printf("\n");
}

int main(void) {
    state s = {};
    update(&s, (msg){.kind = MSG_ADD, .text = "milk"});
    update(&s, (msg){.kind = MSG_ADD, .text = "tea"});
    update(&s, (msg){.kind = MSG_TOGGLE, .index = 0});
    view(&s); /* вывод: 2: +milk -tea */
    update(&s, (msg){.kind = MSG_CLEAR_DONE});
    view(&s); /* вывод: 1: -tea */
    int rc = 0;
    for (int i = 0; i < 4; i++) rc = update(&s, (msg){.kind = MSG_ADD, .text = "x"});
    printf("%d\n", rc); /* вывод: -28 */
}
```

Сообщение это данные: его можно записать в журнал, воспроизвести в тесте и отправить из другого потока. Число невыполненных дел в `state` не хранится: производное значение считают в `view`, иначе оно рассинхронизируется при первой правке в обход. `update` копирует `text` в `state`, а не запоминает указатель: сообщение заимствует строку только до возврата.

#### Подводные камни

- Обработчик виджета пишет поле `state` напрямую, минуя `update`. Журнал команд, уведомления и тест не видят правку, и односторонний поток превращается в обычный клубок.
- `view` с побочным эффектом (сброс флага, запрос к диску). Показ вызывают в любой момент и сколько угодно раз, поэтому эффекты выполняет `update` или отдельный список эффектов, который разбирает цикл.
- Долгая работа в `update` (диск, сеть) замораживает интерфейс. `update` быстрый, долгое уходит в рабочий поток (практика про поток интерфейса ниже).
- Копия большого состояния в сообщении. Сообщение несёт идентификатор или хэндл ([хэндлы](21-patterns.md)) и небольшой набор параметров, а не снимок данных.

### Описывай действия пользователя данными: команды, горячие клавиши, отмена

Действие, оформленное данными (вид и аргумент), можно привязать к клавише таблицей, записать в журнал и отменить, а действие, зашитое в обработчик кнопки, нельзя ничего из этого. Команда это то же сообщение для `update`, горячие клавиши это таблица `клавиша -> команда`, а отмена строится на журнале. Есть два способа отката: хранить обратную команду (для каждой выполненной команды в журнал кладут команду, возвращающую прежнее состояние) или хранить прежнее состояние целиком (снимок или его изменённая часть). Обратные команды дёшевы по памяти; снимки проще и надёжнее, когда состояние небольшое.

```c
#include <errno.h>
#include <stdio.h>

typedef enum { CMD_ADD, CMD_SET, CMD_UNDO } cmd_kind;
typedef struct { cmd_kind kind; int arg; } cmd;
typedef struct { int value; cmd undo[8]; int n; } doc;
typedef struct { char key; cmd c; } binding;

static const binding keymap[] = {
    {'+', {CMD_ADD, 1}}, {'-', {CMD_ADD, -1}}, {'0', {CMD_SET, 0}}, {'u', {CMD_UNDO, 0}},
};

static void apply(doc *d, cmd c) {
    if (c.kind == CMD_ADD) d->value += c.arg;
    else if (c.kind == CMD_SET) d->value = c.arg;
}

/* run - выполняет команду и кладёт в журнал обратную. Возврат: 0, -ENOENT (нечего отменять), -ENOSPC. */
static int run(doc *d, cmd c) {
    if (c.kind == CMD_UNDO) {
        if (d->n == 0) return -ENOENT;
        apply(d, d->undo[--d->n]);
        return 0;
    }
    if (d->n == 8) return -ENOSPC;
    d->undo[d->n++] = c.kind == CMD_ADD ? (cmd){CMD_ADD, -c.arg} : (cmd){CMD_SET, d->value};
    apply(d, c);
    return 0;
}

static int feed(doc *d, const char *keys) {
    int rc = 0;
    for (; *keys; keys++) {
        rc = -EINVAL; /* клавиша не привязана */
        for (size_t i = 0; i < sizeof keymap / sizeof keymap[0]; i++)
            if (keymap[i].key == *keys) { rc = run(d, keymap[i].c); break; }
    }
    return rc;
}

int main(void) {
    doc d = {};
    feed(&d, "++0");
    printf("%d\n", d.value); /* вывод: 0 */
    feed(&d, "uu");
    printf("%d\n", d.value); /* вывод: 1 */
    int rc = feed(&d, "uuu");
    printf("%d %d\n", d.value, rc); /* вывод: 0 -2 */
}
```

Отмена не пишет в журнал и идёт тем же путём, что любая другая команда: в приложении она проходит через `update`, поэтому уведомления подписчиков и перерисовка срабатывают так же, как при обычной правке. Таблица клавиш это данные: её можно загрузить из настроек и показать в меню. Группировку подряд набранных символов в одну запись журнала и связанные правки текста как транзакцию разбирает [глава про техники редактора](25-text-editing.md); повтор (redo) делают вторым стеком, который очищается при любой новой команде.

#### Подводные камни

- Обратная команда, не возвращающая состояние точно. `CMD_ADD` с обрезкой по границам (значение упёрлось в максимум) откатывается вычитанием с другим результатом; для таких команд храни прежнее значение (`CMD_SET` со старым значением, как в примере для `SET`) или снимок.
- Команда с указателем на объект, который удалён позже. Отмена работает с мёртвым указателем; в команде хранят хэндл ([паттерны](21-patterns.md)), а устаревший хэндл при проверке даёт отказ.
- Необратимое действие (удаление файла, отправка по сети) в журнале. Такие команды не журналируют и подтверждают у пользователя заранее.
- Журнал без предела. Задай глубину и вытесняй старейшие записи; журнал в примере фиксированного размера и возвращает `-ENOSPC`, что для настоящей отмены лучше заменить вытеснением.
- Состояние, не входящее в команду (выделение, прокрутка, фокус). После отмены интерфейс показывает правильные данные, но курсор в другом месте; решай заранее, что входит в запись журнала.

## Построение интерфейса

### Выбирай режим построения: немедленный или сохраняемый

Режим определяет, где живёт состояние виджета, поэтому его выбирают до написания первого виджета. Немедленный режим (immediate mode) заново строит интерфейс каждый кадр прямо из `state`: вызов `button()` и рисует кнопку, и возвращает `true`, если по ней щёлкнули, а объектов-виджетов нет. Сохраняемый режим (retained mode) один раз создаёт дерево объектов-виджетов и меняет его по событиям.
| Признак | Немедленный режим | Сохраняемый режим |
|---|---|---|
| Где состояние виджета | в `state` приложения; между кадрами хранятся только hot и active по идентификатору | в объекте виджета; его надо согласовывать с `state` |
| Код | линейный: условие и вызов | создание, подписки, уничтожение |
| Стоимость кадра | перестраивается всё видимое | пропорциональна изменениям (инвалидация) |
| Сложные виджеты (текстовое поле, прокрутка) | состояние хранят рядом по идентификатору | поля объекта |
| Раскладка по размерам потомков | второй проход или задержка на кадр | двухпроходный обход дерева |
| Подходит | инструменты, панели отладки, небольшие приложения | сложные долгоживущие интерфейсы с большим деревом |

По умолчанию бери немедленный режим: меньше кода и нет второго источника правды. Сохраняемый режим оправдан, когда дерево велико, а изменяется редко, или когда нужны долгоживущие объекты (окна, нативные элементы, доступность).

Ниже минимальная основа немедленного режима: мышь эмулируется массивом по кадрам. Идентификатор виджета это хеш метки: объекта, у которого можно хранить состояние, нет, поэтому состояние между кадрами хранится по идентификатору. `hot` это виджет под указателем, `active` виджет, на котором нажата кнопка. Щелчок засчитывается, когда кнопку нажали и отпустили на одном виджете. Метки собираются в арене кадра ([память](04-memory-ownership.md)): `arena_init` в начале кадра сбрасывает все метки разом. Арена повторена из той главы, чтобы пример собирался.

```c
/* arena.h */
#ifndef ARENA_H
#define ARENA_H
#include <stddef.h>

typedef struct { char *beg, *end; } arena;

arena arena_init(void *buf, size_t cap);
void *arena_alloc(arena *a, size_t size, size_t align, size_t count);

#define NEW(a, T, n) ((T *)arena_alloc((a), sizeof(T), alignof(T), (n)))
#endif
```

```c
/* arena.c */
#include "arena.h"
#include <stdint.h>
#include <stdlib.h>
#include <string.h>

arena arena_init(void *buf, size_t cap) { return (arena){buf, (char *)buf + cap}; }

void *arena_alloc(arena *a, size_t size, size_t align, size_t count) {
    size_t pad = -(uintptr_t)a->beg & (align - 1);
    size_t room = (size_t)(a->end - a->beg);
    if (pad > room || (count && size > (room - pad) / count)) abort();
    char *p = a->beg + pad;
    a->beg = p + size * count;
    return memset(p, 0, size * count);
}
```

```c
/* main.c */
#include "arena.h"
#include <stdint.h>
#include <stdio.h>

typedef struct { int x, y; bool down; } mouse;
typedef struct { int x, y, w, h; } rect;
typedef struct { mouse in; uint32_t hot, active; arena frame; } ui;

static uint32_t id_of(const char *s) { /* FNV-1a */
    uint32_t h = 2166136261u;
    for (; *s; s++) h = (h ^ (unsigned char)*s) * 16777619u;
    return h;
}

static bool button(ui *u, rect r, const char *label) {
    uint32_t id = id_of(label);
    if (u->in.x >= r.x && u->in.x < r.x + r.w && u->in.y >= r.y && u->in.y < r.y + r.h) u->hot = id;
    bool clicked = false;
    if (u->active == id && !u->in.down) { clicked = u->hot == id; u->active = 0; }
    else if (u->hot == id && u->in.down && !u->active) u->active = id;
    return clicked;
}

int main(void) {
    static char mem[256];
    ui u = {};
    const mouse script[] = {{45, 5, false}, {45, 5, true}, {45, 5, false}, {5, 5, true}, {60, 5, false}};
    int clicks = 0;
    for (size_t f = 0; f < sizeof script / sizeof script[0]; f++) {
        u.frame = arena_init(mem, sizeof mem); /* сброс арены кадра */
        u.in = script[f];
        u.hot = 0;
        for (int i = 0; i < 2; i++) {
            char *label = NEW(&u.frame, char, 24);
            snprintf(label, 24, "Item %d", i);
            if (button(&u, (rect){i * 40, 0, 40, 10}, label)) { clicks++; printf("click %s\n", label); } /* вывод: click Item 1 */
        }
    }
    printf("%d\n", clicks); /* вывод: 1 */
}
```

На кадрах 1 и 2 нажали и отпустили кнопку `Item 1`: один щелчок. На кадрах 3 и 4 нажали на `Item 0`, а отпустили вне её: `active` сбрасывается без щелчка. Размер арены кадра выбирают по худшему случаю, нехватка места завершает процесс.

В сохраняемом режиме состояние лежит в самих объектах, поэтому главные вопросы это владение и инвалидация. Дерево владеет детьми: уничтожение родителя освобождает поддерево, а у каждого виджета есть признак «нужно перерисовать» (`dirty`). Инвалидация поднимается к корню и останавливается на уже помеченном предке; это верно, пока выполняется инвариант «помеченный узел имеет помеченных предков», который восстанавливается сбросом признаков при обходе сверху вниз.

```c
#include <stdio.h>
#include <stdlib.h>

typedef struct widget { struct widget *parent, *first, *next; bool dirty; } widget;

static widget *widget_new(widget *parent) {
    widget *w = calloc(1, sizeof *w);
    if (!w) abort();
    w->parent = parent;
    if (parent) { w->next = parent->first; parent->first = w; }
    return w;
}

/* widget_invalidate - помечает виджет и предков; возврат: сколько узлов помечено заново. */
static int widget_invalidate(widget *w) {
    int n = 0;
    for (; w && !w->dirty; w = w->parent) { w->dirty = true; n++; }
    return n;
}

/* widget_destroy - владеет поддеревом: освобождает детей, затем себя. */
static void widget_destroy(widget *w) {
    for (widget *c = w->first, *nx; c; c = nx) { nx = c->next; widget_destroy(c); }
    free(w);
}

int main(void) {
    widget *root = widget_new(nullptr), *panel = widget_new(root), *leaf = widget_new(panel);
    printf("%d\n", widget_invalidate(leaf)); /* вывод: 3 */
    printf("%d\n", widget_invalidate(leaf)); /* вывод: 0 */
    widget_destroy(root);
}
```

Данные виджет получает из `state` тем же способом, что и `view`: поля виджета это проекция, которую обновляют из `state` при инвалидации, а не второй источник правды, и обратно в `state` пишут только через `update`.

#### Подводные камни

- Две кнопки с одинаковой меткой получают один идентификатор и делят `hot` и `active`: нажатие на одной активирует обе. Добавляй в хеш индекс или родительскую область (`id_of` от пары «область, метка») и не строй идентификатор из текста, который переводится или меняется.
- Хранить в `hot` и `active` указатель на метку из арены кадра. После сброса арены он висит; храни хеш, а не указатель.
- `hot` сбрасывается в начале кадра: если виджет, нарисованный раньше, не увидел `hot`, поставленный позже, реакция опаздывает на кадр. Для интерфейсов с наложением считай `hot` до рисования или принимай задержку.
- Уничтожение виджета отдельно от родителя без отвязки от списка детей. Родитель держит указатель на освобождённый узел; перед `free` виджет убирают из списка родителя.
- Инвалидация без поднятия к предкам, или сброс `dirty` у предка при помеченном потомке. Инвариант нарушается, и часть дерева не перерисовывается.
- Подписки на `state` у объектов-виджетов (практика про отписку ниже): уничтожение виджета без отписки оставляет обработчик с мёртвым указателем.

## Уведомления и потоки

### Рассылай изменения подписчикам безопасно

Несколько частей интерфейса зависят от одного значения, и вызывать их напрямую из того, кто значение меняет, значит связать всё со всем, поэтому источник хранит список подписчиков (функция и `user_data`, [интерфейсы и callback](07-api-and-modules.md)) и рассылает им изменения. Подписка возвращает хэндл с индексом и поколением ([хэндлы с поколением](21-patterns.md)), по которому отписываются и проверяют живость. Запись значения не вызывает подписчиков: `obs_set` только записывает значение и ставит `dirty`, а `obs_flush` вызывается один раз за кадр или за итерацию цикла и доставляет итоговое значение, поэтому десять правок за кадр дают одно уведомление.

```c
/* obs.h */
#ifndef OBS_H
#define OBS_H
#include <stdint.h>

#define OBS_SUBS 4
typedef void (*obs_fn)(void *user_data, int value);
typedef struct { uint32_t idx, gen; } obs_sub; /* gen == 0: недействителен */
typedef struct { obs_fn fn; void *user_data; uint32_t gen; } obs_slot;
typedef struct { obs_slot s[OBS_SUBS]; int value; bool dirty, flushing; } obs;

/* obs_subscribe - при нехватке слотов возвращает хэндл с gen == 0. */
obs_sub obs_subscribe(obs *o, obs_fn fn, void *user_data);
/* obs_unsubscribe - false для недействительного хэндла. Безопасна изнутри обработчика. */
bool obs_unsubscribe(obs *o, obs_sub h);
void obs_set(obs *o, int value);
/* obs_flush - 0 или -ELOOP (обработчики не успокоились за 8 кругов). Только поток интерфейса. */
int obs_flush(obs *o);
#endif
```

```c
/* obs.c */
#include "obs.h"
#include <errno.h>

obs_sub obs_subscribe(obs *o, obs_fn fn, void *user_data) {
    for (uint32_t i = 0; i < OBS_SUBS; i++)
        if (!o->s[i].fn) {
            o->s[i].fn = fn;
            o->s[i].user_data = user_data;
            return (obs_sub){i, ++o->s[i].gen};
        }
    return (obs_sub){};
}

bool obs_unsubscribe(obs *o, obs_sub h) {
    if (h.idx >= OBS_SUBS || !o->s[h.idx].fn || o->s[h.idx].gen != h.gen) return false;
    o->s[h.idx].fn = nullptr;
    return true;
}

void obs_set(obs *o, int value) { o->value = value, o->dirty = true; }

int obs_flush(obs *o) {
    if (o->flushing) return 0; /* повторный вход: внешний цикл доделает */
    o->flushing = true;
    int rc = 0;
    for (int round = 0; o->dirty && rc == 0; round++) {
        o->dirty = false;
        int v = o->value; /* круг доставляет значение на его начало */
        obs_sub snap[OBS_SUBS];
        int n = 0;
        for (uint32_t i = 0; i < OBS_SUBS; i++)
            if (o->s[i].fn) snap[n++] = (obs_sub){i, o->s[i].gen};
        for (int k = 0; k < n; k++) {
            obs_slot *sl = &o->s[snap[k].idx];
            if (sl->fn && sl->gen == snap[k].gen) sl->fn(sl->user_data, v);
        }
        if (round == 7 && o->dirty) rc = -ELOOP;
    }
    o->flushing = false;
    return rc;
}
```

Три защиты в `obs_flush`. Снимок хэндлов, сделанный до первого вызова, не зависит от изменений списка во время рассылки, а проверка поколения перед каждым вызовом пропускает подписчика, которого успели отписать (в том числе соседним обработчиком). Флаг `flushing` превращает повторный вход в пометку `dirty`: внешний цикл сам сделает ещё круг. Предел кругов не даёт обработчикам, которые меняют значение друг за другом, зациклить интерфейс; такое срабатывание означает циклическую зависимость и считается ошибкой.

```c
/* main.c */
#include "obs.h"
#include <stdio.h>

typedef struct { obs *o; obs_sub victim; } killer;
static char logbuf[64];
static size_t logn;

static void note(char tag, int v) { logn += (size_t)snprintf(logbuf + logn, sizeof logbuf - logn, "%c%d ", tag, v); }
static void killer_fn(void *ud, int v) { killer *k = ud; note('K', v); obs_unsubscribe(k->o, k->victim); }
static void tag_fn(void *ud, int v) { note(*(char *)ud, v); }
static void clamp_fn(void *ud, int v) { if (v > 10) obs_set(ud, 10); }

int main(void) {
    obs o = {};
    killer k = {&o, {}};
    char a = 'A', b = 'B';
    obs_subscribe(&o, killer_fn, &k);
    k.victim = obs_subscribe(&o, tag_fn, &b);
    obs_subscribe(&o, tag_fn, &a);
    obs_set(&o, 1), obs_set(&o, 2), obs_set(&o, 3); /* склейка: одно уведомление */
    obs_flush(&o);
    puts(logbuf); /* вывод: K3 A3 */
    logn = 0, logbuf[0] = 0;
    obs_subscribe(&o, clamp_fn, &o);
    obs_set(&o, 15);
    printf("%d\n", obs_flush(&o)); /* вывод: 0 */
    puts(logbuf); /* вывод: K15 A15 K10 A10 */
}
```

Три правки за кадр дали одно уведомление `K3 A3`, подписчик `B` не вызван: `K` отписал его раньше. Значение 15 вызвало второй круг, потому что `clamp_fn` из обработчика записал 10.

#### Подводные камни

- Порядок вызова подписчиков не часть контракта: он зависит от того, какой слот был свободен. Логику, требующую порядка, не строй на подписках.
- `obs` не потокобезопасен: подписки, запись и рассылка идут только из потока интерфейса (практика про потоки ниже). Рассылка под мьютексом блокирует всех, кому он нужен, а обработчик, берущий тот же мьютекс, виснет.
- Подписчик, который в обработчике меняет то же значение, получает лишний круг при каждом срабатывании; если значение не стабилизируется, срабатывает `-ELOOP`. Обработчик, меняющий значение, должен приходить к неподвижной точке (как `clamp_fn`).
- Нехватка слотов даёт хэндл с `gen == 0`. Результат подписки проверяют, иначе объект считает себя подписанным.
- Доставка итогового значения вместо каждого изменения: если подписчику нужен каждый шаг (журнал, анимация по шагам), отправляй сообщение в `update` (практика про состояние выше), а не склеивай.

### Отписывай обработчик до уничтожения объекта

Типичная ошибка интерфейсов: объект подписался на источник, передав себя как `user_data`, объект уничтожили, а источник остался и при следующей рассылке вызывает обработчик с указателем на освобождённую память. Правило: у каждой подписки есть владелец, он хранит хэндл и отписывается в деструкторе до `free`, подписка не живёт дольше подписчика. Объект запоминает источник и хэндл (модуль `obs` из предыдущей практики) и отписывается первым действием деструктора.

```c
/* main.c */
#include "obs.h"
#include <stdio.h>
#include <stdlib.h>

typedef struct { obs *src; obs_sub sub; int shown; } label;

static void label_on_change(void *user_data, int v) { ((label *)user_data)->shown = v; }

static label *label_new(obs *src) {
    label *l = calloc(1, sizeof *l);
    if (!l) abort();
    l->src = src;
    l->sub = obs_subscribe(src, label_on_change, l);
    return l;
}

/* label_destroy - отписывается до free: после возврата источник не знает о label. */
static void label_destroy(label *l) {
    obs_unsubscribe(l->src, l->sub);
    free(l);
}

int main(void) {
    obs o = {};
    label *l = label_new(&o);
    obs_set(&o, 5);
    obs_flush(&o);
    printf("%d\n", l->shown); /* вывод: 5 */
    label_destroy(l);
    obs_set(&o, 6);
    printf("%d\n", obs_flush(&o)); /* вывод: 0 */
}
```

Без отписки в деструкторе получается ошибка, которую находит ASan (`heap-use-after-free` на записи в `shown`).

```c
/* Ошибка: объект уничтожен, обработчик остался подписанным (UB: запись в освобождённую память) */
#include <stdio.h>
#include <stdlib.h>

typedef void (*fn)(void *user_data, int value);
static fn g_fn;
static void *g_ud; /* один подписчик для краткости */

typedef struct { int shown; } label;
static void label_on_change(void *ud, int v) { ((label *)ud)->shown = v; }

int main(void) {
    label *l = malloc(sizeof *l);
    if (!l) abort();
    g_fn = label_on_change;
    g_ud = l;
    free(l); /* окно закрыли, деструктор не отписался */
    g_fn(g_ud, 5);
}
```

Если объект уничтожают во время рассылки, например соседний обработчик, снимок и проверка поколения в `obs_flush` пропускают его. Вместо указателя в `user_data` можно хранить хэндл объекта из пула ([хэндлы](21-patterns.md)): после уничтожения `pool_get` вернёт отказ, и обработчик тихо выйдет.

#### Подводные камни

- Объект уничтожает себя из собственного обработчика. Рассылка безопасна, но сам обработчик после `label_destroy` не должен трогать объект.
- Источник уничтожен раньше подписчика: указатель на источник в подписчике (`src`) указывает на несуществующий `obs`, и `obs_unsubscribe` читает мёртвую память. Подписчиков уничтожают первыми или дают источнику и подписчикам общего владельца (одну арену, одну сцену).
- Объект с несколькими подписками теряет хэндлы и не может отписаться от части. Храни все хэндлы в объекте и отписывай их в одном месте деструктора.

### Держи состояние в потоке интерфейса

Состояние, дерево виджетов и подписки читают `view` и обработчики без блокировок, поэтому ими владеет один поток, а рабочий поток не трогает ни их, ни `obs`. Он отправляет сообщение в потокобезопасную очередь ([очередь на мьютексе и condvar](12-concurrency.md)), поток интерфейса вынимает сообщения и передаёт их в `update`. Так гонки нет по построению: в `state` пишет только один поток.

Очередь должна ещё будить цикл. Цикл на `poll` будит запись байта в self-pipe ([системный ввод-вывод](13-system-io.md)); в примере поток интерфейса просто ждёт на condvar очереди.

```c
#include <errno.h>
#include <pthread.h>
#include <stdio.h>

typedef enum { MSG_PROGRESS, MSG_DONE } msg_kind;
typedef struct { msg_kind kind; int value; } msg;
typedef struct { msg buf[16]; int head, count; pthread_mutex_t mu; pthread_cond_t cv; } mailbox;
typedef struct { int total, done; } state;

/* mbox_post - из любого потока. Возврат: 0 или -EAGAIN (очередь полна). */
static int mbox_post(mailbox *q, msg m) {
    int rc = 0;
    pthread_mutex_lock(&q->mu);
    if (q->count == 16) rc = -EAGAIN;
    else { q->buf[(q->head + q->count++) % 16] = m; pthread_cond_signal(&q->cv); }
    pthread_mutex_unlock(&q->mu);
    return rc;
}

/* mbox_take - ждёт сообщение; только поток интерфейса. */
static msg mbox_take(mailbox *q) {
    pthread_mutex_lock(&q->mu);
    while (q->count == 0) pthread_cond_wait(&q->cv, &q->mu);
    msg m = q->buf[q->head];
    q->head = (q->head + 1) % 16, q->count--;
    pthread_mutex_unlock(&q->mu);
    return m;
}

static void update(state *s, msg m) { if (m.kind == MSG_PROGRESS) s->total += m.value; else s->done++; }

static void *worker(void *arg) {
    for (int i = 1; i <= 2; i++) mbox_post(arg, (msg){MSG_PROGRESS, i});
    mbox_post(arg, (msg){MSG_DONE, 0});
    return nullptr;
}

int main(void) {
    mailbox q = {.mu = PTHREAD_MUTEX_INITIALIZER, .cv = PTHREAD_COND_INITIALIZER};
    state s = {};
    pthread_t t[3];
    for (int i = 0; i < 3; i++) pthread_create(&t[i], nullptr, worker, &q);
    while (s.done < 3) update(&s, mbox_take(&q)); /* цикл интерфейса */
    for (int i = 0; i < 3; i++) pthread_join(t[i], nullptr);
    printf("total=%d done=%d\n", s.total, s.done); /* вывод: total=9 done=3 */
}
```

Порядок сообщений от разных потоков не определён, но итог не зависит от него. `state` читает и пишет только `main`, блокировка нужна одной очереди.

Если цикл событий принадлежит тулкиту, `update` и рассылку вызывают из его callback, а очередь отображается на вызов «выполнить функцию в потоке интерфейса», который есть у каждого тулкита: рабочий поток вызывает его, передав сообщение, и функция вызывает `update`. API тулкитов в книге не разбирается.

#### Подводные камни

- Рабочий поток пишет в `state` или трогает виджеты «только на минуту». Это гонка данных, которую `view` в потоке интерфейса не защищает ничем; результат работы приходит только сообщением.
- Устаревший результат. Пользователь начал новый запрос, а ответ старого пришёл позже; кладите в сообщение номер запроса, а `update` отбрасывает ответы с неактуальным номером.
- Сообщение с указателем на данные потока. Владение передаётся явно: сообщение владеет выделенной памятью, получатель освобождает её в `update`, рабочий после отправки её не трогает ([владение](04-memory-ownership.md)).
- Неограниченная очередь копит сообщения быстрее, чем интерфейс их разбирает. Предел длины, как в примере, нужен вместе с политикой переполнения: слить однотипные сообщения (последний прогресс заменяет предыдущий) или отказать.
- Блокировка потока интерфейса на ожидании рабочего потока (`join`, ожидание результата). Окно перестаёт отвечать; результат только через сообщение.

## Платформа

### Прячь платформу за таблицей операций

Всё, что знает про окно, ввод и рисование, закрывают таблицей операций ([интерфейсы](07-api-and-modules.md)): логика приложения получает события и показывает кадры только через неё, поэтому она запускается без окна, а тест подаёт сообщения и проверяет `state`. Боевая платформа (тулкит, собственный цикл на `poll` из [главы про системный ввод-вывод](13-system-io.md)) реализует ту же таблицу.

```c
#include <stdio.h>

typedef enum { MSG_INC, MSG_QUIT } msg_kind;
typedef struct { msg_kind kind; } msg;
typedef struct { int count; bool quit; } state;

typedef struct platform_ops {
    bool (*next_msg)(void *ctx, msg *out);        /* false: событий больше нет */
    void (*present)(void *ctx, const char *text); /* показать кадр */
} platform_ops;
typedef struct platform { const platform_ops *vt; void *ctx; } platform;

static void update(state *s, msg m) { if (m.kind == MSG_INC) s->count++; else s->quit = true; }

/* app_run - логика приложения, про окно ничего не знает. Возврат: число показанных кадров. */
static int app_run(platform p, state *s) {
    int frames = 0;
    msg m;
    while (!s->quit && p.vt->next_msg(p.ctx, &m)) {
        char text[32];
        update(s, m);
        snprintf(text, sizeof text, "count=%d", s->count);
        p.vt->present(p.ctx, text);
        frames++;
    }
    return frames;
}

typedef struct { const msg *script; int n, pos; char last[32]; } fake;
static bool fake_next(void *ctx, msg *out) {
    fake *f = ctx;
    if (f->pos == f->n) return false;
    *out = f->script[f->pos++];
    return true;
}
static void fake_present(void *ctx, const char *text) { snprintf(((fake *)ctx)->last, 32, "%s", text); }
static const platform_ops fake_ops = {fake_next, fake_present};

int main(void) {
    msg script[] = {{MSG_INC}, {MSG_INC}, {MSG_QUIT}, {MSG_INC}};
    fake f = {script, 4, 0, ""};
    state s = {};
    int frames = app_run((platform){&fake_ops, &f}, &s);
    printf("%d %s %d\n", frames, f.last, s.count); /* вывод: 3 count=2 2 */
}
```

Тестовая платформа подаёт сценарий и запоминает последний показанный кадр: четвёртое сообщение после `MSG_QUIT` цикл не берёт. Тот же приём годится для интеграционных тестов: сценарий из сообщений и проверка `state` или текста кадра заменяют ручной прогон в окне, а отладочный режим воспроизводит записанный сценарий (сообщения это данные).

#### Подводные камни

- Платформенный тип (дескриптор окна, структура события тулкита) в сигнатурах логики приложения. Зависимость возвращается, и она снова не собирается без окна; наружу выходят только свои типы (`msg`, `state`, текст кадра).
- Тестовая платформа, ведущая себя иначе, чем боевая: события приходят сразу, а в боевой с задержкой и пачками. Контракт таблицы (когда `next_msg` блокируется, можно ли звать `present` из callback) описывают комментарием у типа.
- Слишком подробная таблица (операция на каждый пиксель). Таблица описывает то, что нужно логике: события, кадр, время, буфер обмена; рисование на уровне примитивов тоже может быть данными (список команд рисования).

## Коротко

### Перерисовывай по требованию

Перерисовка каждые 16 мс без изменений жжёт процессор, поэтому цикл ждёт события и перерисовывает кадр только при `dirty`. Ожидание ограничивают временем до ближайшего таймера, а во время анимации кадр идёт по расписанию. Анимацию ведут по дельте времени между кадрами (`pos += speed * dt`), а не по номеру кадра, иначе скорость зависит от частоты кадров.

```c
#include <stdint.h>

/* wait_ms - таймаут для poll: -1 ждать вечно, 0 не ждать. */
int wait_ms(bool animating, int64_t next_timer, int64_t now) {
    if (animating) return 16;
    return next_timer < 0 ? -1 : (int)(next_timer > now ? next_timer - now : 0);
}
```

Значение передают в `poll` из [главы про системный ввод-вывод](13-system-io.md); если событие пришло, цикл применяет сообщения, затем `obs_flush`, затем перерисовывает при `dirty`. Время берут из интерфейса часов ([паттерны](21-patterns.md)), чтобы анимацию можно было проверить без `sleep`.

### Маршрутизируй события по явным правилам

Мышь идёт к виджету под указателем (hit testing): проверка сверху вниз по порядку отрисовки, первый подходящий получает событие. Клавиатура идёт к виджету с фокусом, а фокус это одно поле в `state` или в корне дерева. Во время перетаскивания указатель захватывают: виджет получает все события мыши, даже когда указатель вышел за его границы, пока кнопка не отпущена. Событие возвращает флаг «обработано»: если виджет его обработал, родитель не пробует его же; если нет, событие всплывает вверх до горячих клавиш приложения.

### Раскладывай за два прохода

Размер виджета часто зависит от размеров потомков, а положение потомка от размера родителя, поэтому раскладка идёт двумя проходами по дереву: снизу вверх каждый виджет сообщает желаемый размер (измерение), сверху вниз родитель назначает размер и положение потомкам (размещение). Измеренный размер кэшируют до инвалидации (`dirty` из практики про режимы); после изменения текста или набора потомков перемеряют только поднимающуюся к корню цепочку.

## Что ещё стоит знать

Масштаб экрана (DPI): координаты и размеры шрифта хранят в логических единицах и умножают на масштаб при рисовании, а изменение масштаба (перенос окна на другой монитор) приходит событием, как любое другое. Текст и локализация требуют шейпинга, переноса строк, двунаправленного текста и правил множественных чисел, поэтому строки интерфейса держат отдельным словарём, а не литералами в коде. Доступность (чтение с экрана, навигация с клавиатуры) требует дерева виджетов с ролями и подписями, которое тулкит строит сам; интерфейс в немедленном режиме без него плохо читается ассистивными технологиями. Готовые тулкиты (GTK, Qt, SDL с отдельными надстройками) берут на себя цикл, окна и рисование, а описанная в главе архитектура остаётся поверх них.
