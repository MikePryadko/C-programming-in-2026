# Производительность

## Измерение

### Сначала измерь, потом оптимизируй

Без измерения оптимизируют не то место, а выигрыш невозможно отличить от шума, поэтому у каждой оптимизации есть один показатель (время на запрос, пропускная способность) и сравнение «до» и «после» на одной машине, одним компилятором и теми же флагами. Одного запуска мало: время колеблется, поэтому измерение повторяют и смотрят на среднее и на относительное отклонение; если отклонение сравнимо с разницей между вариантами, разницы нет. Сборка для измерения такая же, как релизная (`-O2`), а не отладочная и не с санитайзерами.

Главная ловушка микробенчмарка: оптимизатор удаляет вычисление, результат которого не используется. Результат накапливают и выводят, иначе измеряется пустой цикл.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define RUNS 15

static double now(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return (double)t.tv_sec + (double)t.tv_nsec * 1e-9;
}

static long sum(const int *a, size_t n) {
    long s = 0;
    for (size_t i = 0; i < n; i++) s += a[i];
    return s;
}

int main(void) {
    size_t n = 1u << 20;
    int *a = malloc(n * sizeof *a);
    if (!a) abort();
    for (size_t i = 0; i < n; i++) a[i] = (int)(i & 255);

    double t[RUNS], mean = 0, dev = 0;
    long sink = 0; /* результат используется: цикл не будет удалён */
    for (int r = 0; r < RUNS; r++) {
        double t0 = now();
        sink += sum(a, n);
        t[r] = now() - t0;
        mean += t[r] / RUNS;
    }
    for (int r = 0; r < RUNS; r++) dev += (t[r] > mean ? t[r] - mean : mean - t[r]) / RUNS;
    fprintf(stderr, "%.3f ms/run, отклонение %.1f%%\n", mean * 1e3, dev / mean * 100);
    printf("%ld\n", sink); /* вывод: 2005401600 */
    free(a);
    return 0;
}
```

Для длинных программ профилировщик Linux `perf` показывает, где проводится время: `perf stat -r 10 ./prog` повторяет запуск и печатает среднее с разбросом, а `perf record -g ./prog` и `perf report` дают разбивку по функциям (для читаемых стеков собирай с `-fno-omit-frame-pointer`). Оптимизируют то, что оказалось наверху отчёта, а не то, что кажется медленным.

#### Подводные камни

- Инструментация сдвигает время. Санитайзеры, `-O0`, профилировочные счётчики и вывод внутри измеряемого участка меняют соотношения между вариантами; измеряй сборкой без них, а санитайзеры оставь для проверки корректности.
- Результат не использован. Вызов чистой функции или `malloc` без чтения результата исчезает так же, как цикл; накапливай результат, как `sink` выше.
- Один запуск и холодный кэш. Первый проход включает подкачку страниц и прогрев кэша; делай прогревочный проход и повторяй измерение, а отклонение сравнивай с ожидаемым выигрышем.
- Часы. Для интервалов бери `CLOCK_MONOTONIC`: `time` и `CLOCK_REALTIME` прыгают при коррекции времени.
- Данные не как в работе. Размер и порядок входа, при которых узкое место проявляется, должны быть такими, как у реальной нагрузки: на малых массивах всё помещается в кэш и выводы переворачиваются.

## Данные и алгоритмы

### Выбирай алгоритм и структуру данных раньше микрооптимизаций

Замена асимптотики даёт во много раз больше, чем любые правки внутри цикла, поэтому сначала спрашивают, сколько раз и над каким объёмом работает код, и только потом тонко настраивают. Типичный случай: поиск в массиве на каждый запрос; один раз отсортированный массив с бинарным поиском (`qsort` и `bsearch` из стандартной библиотеки) или хеш-таблица ([контейнеры](09-containers-and-generics.md)) превращают запрос из прохода по всем элементам в несколько сравнений.

```c
#include <stdbool.h>
#include <stddef.h>
#include <stdio.h>
#include <stdlib.h>

static int cmp_int(const void *x, const void *y) {
    int a = *(const int *)x, b = *(const int *)y;
    return (a > b) - (a < b);
}

/* O(n) на запрос */
static bool find_linear(const int *a, size_t n, int key) {
    for (size_t i = 0; i < n; i++)
        if (a[i] == key) return true;
    return false;
}

/* a отсортирован: O(log n) на запрос */
static bool find_sorted(const int *a, size_t n, int key) {
    return bsearch(&key, a, n, sizeof *a, cmp_int) != nullptr;
}

int main(void) {
    int a[] = {42, 7, 19, 3, 88, 61, 25, 14};
    size_t n = sizeof a / sizeof *a;
    printf("%d\n", find_linear(a, n, 61)); /* вывод: 1 */
    qsort(a, n, sizeof *a, cmp_int);
    printf("%d %d\n", find_sorted(a, n, 61), find_sorted(a, n, 62)); /* вывод: 1 0 */
    return 0;
}
```

При 20000 запросах к массиву из `n` случайных `int` (сортировка включена в вариант с бинарным поиском) на сотне элементов разница в пределах шума, на тысячах линейный поиск медленнее в разы, на сотне тысяч на порядок и больше. На малых `n` разницы почти нет, на больших она растёт вместе с `n`; выбирай по реальному размеру данных, а не «на вырост». Сортировка окупается, когда запросов заметно больше, чем один; для частых вставок между запросами нужна другая структура (хеш-таблица, дерево).

#### Подводные камни

- Функция сравнения возвращает `a - b`. Разность переполняется на больших значениях, и порядок ломается ([целые типы](02-types-and-ub.md)); сравнивай через `(a > b) - (a < b)`, как выше (компараторы для `qsort` разобраны в [контейнерах](09-containers-and-generics.md)).
- `bsearch` на неотсортированных данных. Результат произвольный, диагностики нет; сортируй после каждого изменения либо держи данные упорядоченными при вставке.
- Оптимизация без измерения реального размера. Линейный поиск по десяти элементам обычно быстрее любой структуры; смени алгоритм, когда профиль и размер данных это оправдывают.
- Квадратичный код, спрятанный в цикле: `strlen` или `strcat` внутри цикла по строке, линейный `contains` в цикле по данным. Ищи вложенный проход по тем же данным ([построитель строк](05-strings-and-buffers.md)).

### Располагай данные так, как их читает горячий цикл

Процессор читает память строками кэша, поэтому скорость цикла определяется тем, сколько нужных ему байт лежит рядом: плотные данные в порядке обхода быстрее разреженных. Три приёма: сжимай структуры, храни в массиве только то, что читает цикл, и обходи многомерные массивы по тому индексу, который меняется в памяти быстрее всего.

Порядок полей влияет на дополнение (padding): компилятор выравнивает каждое поле по его размеру, и поля, упорядоченные от крупных к мелким, расходуют меньше места.

```c
#include <stddef.h>
#include <stdio.h>

typedef struct { char tag; double value; char flag; } loose;
typedef struct { double value; char tag; char flag; } dense;

int main(void) {
    /* для платформ, где double выравнивается по 8 байт (x86-64, AArch64) */
    printf("%zu %zu\n", sizeof(loose), sizeof(dense)); /* вывод: 24 16 */
    printf("%zu %zu\n", offsetof(loose, value), offsetof(loose, flag)); /* вывод: 8 16 */
    return 0;
}
```

Если цикл читает одно поле большого количества объектов, массив структур заставляет читать целые структуры, а массив полей (одно поле в отдельном массиве) читает только нужное.

```c
#include <stddef.h>

typedef struct { double x, y, z, vx, vy, vz; int id; } particle;
typedef struct { double *x, *y, *z, *vx, *vy, *vz; int *id; size_t n; } particles;

double sum_x_aos(const particle *p, size_t n) {
    double s = 0;
    for (size_t i = 0; i < n; i++) s += p[i].x;
    return s;
}

double sum_x_soa(const particles *p) {
    double s = 0;
    for (size_t i = 0; i < p->n; i++) s += p->x[i];
    return s;
}
```

Обход матрицы: внутренний цикл должен идти по подряд лежащим элементам строки, а не по столбцу.

```c
#include <stddef.h>

long sum_rows(const int *m, size_t n) {
    long s = 0;
    for (size_t i = 0; i < n; i++)
        for (size_t j = 0; j < n; j++) s += m[i * n + j];
    return s;
}

long sum_cols(const int *m, size_t n) {
    long s = 0;
    for (size_t j = 0; j < n; j++)
        for (size_t i = 0; i < n; i++) s += m[i * n + j];
    return s;
}
```

Сумма одного поля у миллиона частиц с массивом структур медленнее, чем с массивом полей, примерно вдвое, а обход матрицы 4096 на 4096 по столбцам медленнее обхода по строкам на порядок.

#### Подводные камни

- Массив полей усложняет код: все массивы растут и перемещаются вместе, а один объект уже не лежит в одном месте. Применяй там, где профиль показал узкое место, и скрывай устройство за функциями доступа.
- Упаковка структуры атрибутом `packed` (расширение GCC/Clang) убирает дополнение, но делает поля невыровненными: доступ медленнее, а на некоторых платформах недопустим; порядок полей обычно даёт тот же выигрыш без этого.
- Выигрыш зависит от размера данных. Если всё помещается в кэш, различий нет; проверяй на размере реальной нагрузки.
- Структура с дополнением, записанная в файл или сокет, выдаёт содержимое памяти ([безопасность](12-security.md)).

### Не выделяй память на каждый объект в горячем пути

Каждое `malloc` и `free` содержит работу аллокатора и разбрасывает объекты по куче, поэтому много мелких выделений одного времени жизни выгоднее брать из арены: выделение сдвигает указатель, а освобождение одно на всё ([арены](03-memory-ownership.md)).

```c
#include <stddef.h>

typedef struct { char *beg, *end; } arena;
void *arena_alloc(arena *a, size_t size, size_t align, size_t count); /* см. главу про память */

typedef struct node { long value; struct node *next; } node;

/* Узел из арены вместо calloc: сдвиг указателя, free по узлам не нужен */
long sum_arena(arena a, size_t n) {
    node *head = nullptr;
    for (size_t i = 0; i < n; i++) {
        node *x = arena_alloc(&a, sizeof *x, alignof(node), 1);
        *x = (node){(long)i, head};
        head = x;
    }
    long s = 0;
    for (node *x = head; x; x = x->next) s += x->value;
    return s;
}
```

Если объекты не одного времени жизни, а временный буфер нужен на каждый вызов, его выделяют один раз и переиспользуют, передавая в функцию. На миллионе узлов арена быстрее, чем `calloc` и `free` на каждый узел, на порядок, а один переиспользуемый буфер вместо `malloc` и `free` на вызов при форматировании короткой строки даёт лишь небольшой выигрыш: `malloc` для коротких блоков обычно недорог, а выигрыш зависит от доли работы аллокатора. Профиль показывает, где аллокатор виден на самом деле.

#### Подводные камни

- Арена в первом проходе включает подкачку страниц. Прогревай блок или сравнивай по нескольким проходам.
- Переиспользуемый буфер хранит данные предыдущего вызова. Перед использованием очищай его или записывай нулевой байт, а секреты затирай ([безопасность](12-security.md)).
- Пул и арена держат память до своего освобождения. Для долгоживущих и разнородных объектов с независимым временем жизни это утечка по сути; выбирай арену для данных одной фазы ([пулы](03-memory-ownership.md)).

## Подсказки компилятору

### Ставь restrict только там, где точно нет перекрытия

Квалификатор `restrict` обещает компилятору, что объект, который изменяется через этот указатель, в этой области доступен только через него, поэтому он вправе переставлять и объединять обращения, а при нарушении обещания результат непредсказуем. Типичное применение: функции, в которые приходят входной и выходной буферы, и компилятор иначе вынужден предполагать их перекрытие.

```c
#include <stddef.h>
#include <stdio.h>

/* axpy: y[i] += k * x[i]. x и y не перекрываются: это обещание вызывающего */
void axpy(size_t n, float k, const float *restrict x, float *restrict y) {
    for (size_t i = 0; i < n; i++) y[i] += k * x[i];
}

int main(void) {
    float x[3] = {1, 2, 3}, y[3] = {10, 20, 30};
    axpy(3, 2, x, y);
    printf("%g %g %g\n", (double)y[0], (double)y[1], (double)y[2]); /* вывод: 12 24 36 */
    return 0;
}
```

Нарушение обещания не ловит ни компилятор, ни санитайзеры, а результат зависит от компилятора и уровня оптимизации:

```c
/* Ошибка: dst и src перекрываются, хотя оба параметра помечены restrict */
#include <stddef.h>
#include <stdio.h>

void copy_r(int *restrict dst, const int *restrict src, size_t n) {
    for (size_t i = 0; i < n; i++) dst[i] = src[i];
}

int main(void) {
    int a[9] = {1, 2, 3, 4, 5, 6, 7, 8, 9};
    copy_r(a + 1, a, 8);
    for (int i = 0; i < 9; i++) printf("%d ", a[i]);
    puts("");
    return 0;
}
```

Без оптимизации (`-O0`) цикл копирует поэлементно и размножает первый элемент (`1 1 1 1 1 1 1 1 1`). На `-O2` (Clang и GCC) компилятор, раз буферы по обещанию не пересекаются, заменяет цикл вызовом `memcpy`, а он читает блок раньше записи и печатает `1 1 2 3 4 5 6 7 8`; Clang делает то же уже на `-O1`, GCC только с `-O2`. Сборка с `-fsanitize=address,undefined` отчёта не даёт. Результат зависит от флагов и версии компилятора, поэтому дефект проявляется только после их смены.

Выигрыш от `restrict` скромнее, чем обычно ждут: Clang векторизует такой цикл и без него (отчёт `-Rpass=loop-vectorize` это показывает), а у GCC направление и размер разницы зависят от процессора. Смотри эффект, а не предполагай его.

#### Подводные камни

- `restrict` в публичном API. Обещание часть контракта: запиши в комментарии, что буферы не перекрываются ([контракты API](06-api-and-modules.md)); вызывающий, не знавший о нём, получит неверный результат без диагностики.
- Функция получает два указателя в один массив (часто: сдвиг, сжатие на месте). Здесь `restrict` недопустим; для перекрывающихся диапазонов есть `memmove`.
- Указатель, полученный из `restrict`-указателя (смещение, копия), тоже участвует в обещании: обращайся к объекту только через такое семейство указателей, пока он изменяется.
- Без измерения `restrict` ничего не ускоряет. Прежде чем вносить его и контракт, сравни по `-Rpass=loop-vectorize` (Clang) или `-fopt-info-vec-optimized` (GCC), векторизуется ли цикл без него.

### Проверяй эффект inline и не оптимизируй невидимое

Подстановка (inline) убирает вызов только для маленьких функций в горячем цикле, поэтому её не раздают всем подряд: компилятор сам решает, что подставлять, а `inline` лишь разрешает определение в заголовке ([`static inline` и внешнее определение](06-api-and-modules.md)). Узнай, что произошло на самом деле: Clang печатает решение флагами `-Rpass=inline` и `-Rpass-missed=inline`, GCC флагом `-fopt-info-inline-optimized`.

```sh
clang -std=c23 -O2 -Rpass=inline -Rpass-missed=inline -c util.c
gcc -std=c23 -O2 -fopt-info-inline-optimized -c util.c
```

Подстановка между файлами возможна только при оптимизации на этапе компоновки (раздел ниже). Отчёты оптимизатора есть и для векторизации: `-Rpass=loop-vectorize` и `-Rpass-missed=loop-vectorize` у Clang, `-fopt-info-vec-optimized` у GCC показывают, какие циклы векторизованы, и по ним решают, нужна ли правка.

Не оптимизируй то, что не видно в профиле. Проверки (границ, указателей на `nullptr`, возврата ошибок) и инициализация данных в профиле обычно не видны: цикл с проверкой границы перед каждым обращением отличался от цикла без неё в пределах шума, поэтому защитные проверки убирают только по профилю, а не из соображений скорости. Зато адрес накопителя, переданный в непрозрачную функцию, мешает оптимизатору: если в цикле есть вызов другой непрозрачной функции, компилятор обновляет накопитель в памяти на каждом витке вместо регистра. В горячем цикле накапливай в локальной переменной, адрес наружу не отдавай, а результат возвращай в конце.

#### Подводные камни

- `inline` или `__attribute__((always_inline))` на большой функции. Код раздувается, кэш инструкций переполняется, и выигрыш превращается в потерю; принудительную подстановку ставят по профилю.
- Подстановка из другого файла ожидается без LTO. Определение функции не видно, вызов остаётся; поменяй расположение или включи LTO.
- Оптимизация по догадке. Правка, которая «должна» ускорить, измеряется до и после; без разницы в пределах отклонения её откатывают.
- Микрооптимизация вместо структуры: ручная развёртка, битовые трюки, замена умножения сдвигом. Современный компилятор делает это сам; читаемость и корректность важнее.

## Коротко

### ThinLTO и PGO как флаги сборки

Оптимизация на этапе компоновки (LTO) позволяет компилятору подставлять и оптимизировать функции между файлами, а оптимизация по профилю (PGO) использует реальный запуск, чтобы разместить горячие и холодные ветви; обе включают флагами и проверяют измерением. Режим ThinLTO у Clang масштабируется на большие проекты: `-flto=thin` ставят и при компиляции, и при компоновке. PGO в Clang требует трёх шагов: инструментированная сборка, запуск на типичной нагрузке и сборка с профилем (`llvm-profdata` берут той же версии, что и Clang).

```sh
clang -O2 -flto=thin util.c main.c -o app

clang -O2 -fprofile-instr-generate util.c main.c -o app_inst
LLVM_PROFILE_FILE=app.profraw ./app_inst
llvm-profdata merge -output=app.profdata app.profraw
clang -O2 -fprofile-instr-use=app.profdata util.c main.c -o app_pgo
```

Выигрыш зависит от программы: на маленькой функции из другого файла в горячем цикле ThinLTO подставляет её (`-Rpass=inline` показывает это) и ускоряет цикл в разы, а PGO на том же примере ничего не дал, поэтому оба флага включают по измерению на своей нагрузке.

### Атрибуты unsequenced и reproducible

Атрибуты C23 `[[unsequenced]]` (функция без побочных эффектов, результат зависит только от аргументов) и `[[reproducible]]` (результат может зависеть ещё и от памяти по аргументам) разрешают компилятору объединять и переставлять вызовы; их ставят после списка параметров, а неверная пометка функции с побочными эффектами даёт неопределённое поведение. Clang 19 и 20 и GCC 14 их пропускают с предупреждением, поэтому включают через проверку наличия:

```c
#if __has_c_attribute(unsequenced)
#define FN_UNSEQUENCED [[unsequenced]]
#else
#define FN_UNSEQUENCED
#endif
int square(int x) FN_UNSEQUENCED;
```

## Что ещё стоит знать

Ассемблерные вставки и собственные версии функций `memcpy`, `strlen` и других функций libc писать не нужно: компилятор и libc выбирают векторные реализации под процессор сами, а свои почти всегда медленнее и добавляют ошибки. Векторизацию не пишут вручную, а подбирают форму цикла и данных под отчёты оптимизатора (см. выше).
