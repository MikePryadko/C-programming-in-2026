# Типы, целые числа и неопределённое поведение

## Целые числа

### Проверяй переполнение через ckd_add, ckd_sub, ckd_mul

Знаковое переполнение неопределено, а беззнаковое молча оборачивается по модулю, поэтому и то и другое нельзя оставлять без проверки там, где значение приходит снаружи: размеры, счётчики, смещения. Заголовок `<stdckdint.h>` (C23, работает на Clang 19, Clang 20 и GCC 14) даёт три операции: результат записывается через указатель, а возвращаемое значение `true` означает, что математический результат не поместился в тип приёмника. Тип приёмника может отличаться от типов операндов, так что проверка совмещается с сужением.

```c
#include <errno.h>
#include <limits.h>
#include <stdckdint.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

/* hdr + count * elem; 0 или -EOVERFLOW */
int rec_bytes(size_t count, size_t elem, size_t hdr, size_t *out) {
    size_t n;
    if (ckd_mul(&n, count, elem) || ckd_add(&n, n, hdr)) return -EOVERFLOW;
    *out = n;
    return 0;
}

int main(void) {
    size_t n = 0;
    printf("%d\n", rec_bytes(SIZE_MAX / 2, 4, 8, &n) == -EOVERFLOW); /* вывод: 1 */
    printf("%d\n", rec_bytes(10, 4, 8, &n)); /* вывод: 0 */
    printf("%zu\n", n); /* вывод: 48 */
    int r;
    printf("%d\n", ckd_sub(&r, 0, INT_MIN)); /* вывод: 1 */
    unsigned char small;
    printf("%d\n", ckd_add(&small, 200, 100)); /* вывод: 1 */
    return 0;
}
```

Проверка после операции для знаковых типов не работает: оптимизатор вправе считать, что переполнения не было, и выбрасывает условие целиком (подробнее в практике про оптимизатор ниже).

```c
/* Ошибка: UB, знаковое переполнение происходит до проверки, которой уже нечего ловить */
#include <limits.h>
#include <stdio.h>

int main(int argc, char **argv) {
    (void)argv;
    int a = INT_MAX - 1 + argc;
    if (a + 1 < a) puts("переполнение");
    printf("%d\n", a);
    return 0;
}
```

#### Подводные камни

- `-x`, `abs(x)` и `x / -1` для `INT_MIN` переполняются (результат `2147483648` в `int` не помещается), а `x % -1` неопределено по прямому правилу, хотя математически равно нулю; на x86-64 `INT_MIN / -1` ещё и завершает процесс по `SIGFPE`. Для отрицания безопасна `ckd_sub(&r, 0, x)`, для остального проверяй вход до операции.
- Деление и остаток на ноль неопределены для целых типов: делитель из внешних данных проверяй до операции (`if (d == 0) return -EINVAL;`).
- При `true` в приёмнике остаётся значение по модулю; использовать его нельзя, только вернуть ошибку.
- Clang отвергает `char`, `bool` и перечисления как операнды и приёмник `ckd_*` (GCC принимает, но на это не полагайся): приведи значение к `int` или выбери явный целый тип.
- Беззнаковое оборачивание определено, но в расчёте размера буфера превращается в уязвимость: `n * sizeof(T)` без `ckd_mul` выделяет меньше, чем потом записывается (идиома выделения с проверкой: [аллокации](03-memory-ownership.md)).
- `-fwrapv` делает знаковое переполнение определённым и скрывает ошибку от UBSan; он не заменяет проверок ([инструменты сборки](01-toolchain.md)).

### Считай в size_t и ptrdiff_t, а в узких типах не считай

Арифметика в C выполняется не уже, чем в `int`: операнды `char`, `short`, `uint8_t`, `uint16_t`, `bool` продвигаются в `int`, поэтому переполнение и знаковые эффекты возникают там, где их не ждёшь, а присваивание обратно в узкий тип молча обрезает значение. Размеры, счётчики и индексы держи в `size_t`, разности указателей и всё, что может быть отрицательным, в `ptrdiff_t`; типы с точной шириной (`uint32_t`) оставь для форматов хранения и протоколов.

```c
#include <stdint.h>
#include <stdio.h>

int main(void) {
    uint8_t a = 200, b = 100;
    unsigned char m = 0x0F;
    printf("%d\n", a + b); /* вывод: 300 */
    printf("%d\n", (uint8_t)(a + b)); /* вывод: 44 */
    int inv = ~m;
    printf("%d\n", inv); /* вывод: -16 */
    printf("%d\n", (uint8_t)~m); /* вывод: 240 */
    return 0;
}
```

Сумма `a + b` равна 300, потому что она посчитана в `int`; `~m` даёт `-16`, а не `240`, поэтому сравнение `~m == 0xF0` ложно (GCC предупреждает об этом `-Wsign-compare`). Если нужен результат в узком типе, сужение пиши явно и там, где значение заведомо помещается.

Перебор индексов в обратную сторону на беззнаковом типе требует другой формы цикла: условие `i >= 0` для `size_t` истинно всегда.

```c
/* Ошибка: бесконечный цикл, i >= 0 для size_t всегда истинно, а при n == 0 индекс n - 1 огромен */
#include <stddef.h>

int sum_reversed(const int *v, size_t n) {
    int s = 0;
    for (size_t i = n - 1; i >= 0; i--) s += v[i];
    return s;
}
```

Верная форма: `for (size_t i = n; i-- > 0;)` (условие вычитает после проверки, тело видит `n - 1 ... 0`, пустой массив безопасен).

Сравнение знакового значения с размером и сужение размера в `int` оформляй проверкой, а не приведением:

```c
#include <errno.h>
#include <stdbool.h>
#include <stdckdint.h>
#include <stddef.h>

/* i может быть отрицательным; n - размер массива */
bool idx_ok(ptrdiff_t i, size_t n) { return i >= 0 && (size_t)i < n; }

/* сужение с проверкой: 0 или -ERANGE */
int to_int(size_t n, int *out) { return ckd_add(out, n, 0) ? -ERANGE : 0; }
```

Приведение `(size_t)i` в `idx_ok` безопасно именно потому, что знак проверен слева.

```c
/* Ошибка: sizeof параметра-массива равен размеру указателя, а не массива */
#include <stddef.h>

size_t count(int a[8]) { return sizeof a / sizeof a[0]; }
```

#### Подводные камни

- Смешение знакового и беззнакового. `-1 < sizeof x` ложно: `-1` превращается в `SIZE_MAX`. GCC предупреждает об этом через `-Wsign-compare` (входит в `-Wextra`), Clang на сравнении с отрицательной константой молчит; исправляется проверкой знака до сравнения, как в `idx_ok`.
- Приведение типа глушит `-Wconversion`: `(int)len` ничего не проверяет и только прячет усечение. Сужай через `ckd_add(&dst, src, 0)` или явную проверку диапазона (флаги и набор предупреждений: [сборка](01-toolchain.md)).
- Вычитание беззнаковых `a - b` при `a < b` даёт огромное число; сначала сравни, потом вычитай.
- `uint16_t * uint16_t` считается в знаковом `int` и переполняется уже на `65535 * 65535`; приведи один из множителей к `uint32_t` до умножения.
- Параметр-массив в сигнатуре (`int a[8]`) на деле указатель, поэтому `sizeof` внутри функции бессмыслен; передавай длину отдельным параметром типа `size_t`.
- Знаковость `char` определяется платформой, и аргумент `isalpha` и ему подобных должен быть `unsigned char` ([строки и буферы](05-strings-and-buffers.md)).

### Сдвигай и маскируй только беззнаковые значения

Сдвиг и побитовые операции работают над продвинутым типом, а в `int` легко выйти за знаковый бит: сдвиг влево, при котором результат не помещается в тип, неопределён. Типичная ловушка при разборе бинарных данных: `uint8_t` продвигается в `int`, и `b[0] << 24` для `0x80` не помещается.

```c
#include <inttypes.h>
#include <stdint.h>
#include <stdio.h>

/* big-endian; приведение до сдвига, а не после */
uint32_t load_be32(const uint8_t *p) {
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16) |
           ((uint32_t)p[2] << 8) | (uint32_t)p[3];
}

int main(void) {
    const uint8_t b[4] = {0x80, 1, 2, 3};
    printf("%08" PRIx32 "\n", load_be32(b)); /* вывод: 80010203 */
    return 0;
}
```

```c
/* Ошибка: UB, b[0] продвигается в int, 0x80 << 24 не помещается в int */
#include <stdint.h>
#include <stdio.h>

int main(int argc, char **argv) {
    (void)argv;
    uint8_t b[4] = {0x80, 1, 2, (uint8_t)argc};
    uint32_t v = (uint32_t)(b[0] << 24 | b[1] << 16 | b[2] << 8 | b[3]);
    printf("%u\n", v);
    return 0;
}
```

#### Подводные камни

- Счётчик сдвига должен быть неотрицательным и меньше ширины продвинутого типа: `x << 32` для `uint32_t` неопределён. Счётчик из входных данных проверяй или маскируй (`n & 31`).
- `1 << 31` и `1 << 40` считаются в `int`; пиши `1u << 31` или `UINT64_C(1) << 40`.
- `~1u` имеет ширину `unsigned int`: в выражении `x & ~1u` с 64-битным `x` старшие 32 бита обнуляются. Для 64 бит пиши `x & ~UINT64_C(1)`.
- Сдвиг вправо отрицательного значения определяется реализацией, а влево неопределён; для масок и флагов используй беззнаковые типы целиком.

## Память и объекты

### Инициализируй каждый объект при объявлении

Чтение неинициализированного автоматического объекта неопределено: значение может меняться от чтения к чтению, а оптимизатор вправе считать условие и истинным, и ложным одновременно. ASan и UBSan такое чтение не видят; его ловит только MSan на Clang (`-fsanitize=memory`, отдельным прогоном: он несовместим с ASan в одном бинаре). Поэтому дешевле инициализировать всё сразу: в C23 пустой инициализатор `{}` обнуляет все члены любого агрегата без угадывания типа первого члена.

```c
#include <stdio.h>

typedef struct { char tag; int val; char name[8]; } rec;

int main(void) {
    rec r = {};
    int counts[4] = {};
    rec p = {.tag = 'x', .val = 7};
    printf("%d %d %d\n", r.val, r.name[3], counts[2]); /* вывод: 0 0 0 */
    printf("%d %d\n", p.val, p.name[0]); /* вывод: 7 0 */
    return 0;
}
```

При `flag == false` функция возвращает неинициализированное `x`:

```c
/* Ошибка: x не инициализирован на ветке без присваивания */
#include <stdbool.h>

int pick(bool flag) {
    int x;
    if (flag) x = 1;
    return x;
}
```

Сравнение структур через `memcmp` читает ещё и байты выравнивания между полями, значения которых не определены даже после обнуления структуры (присваивание полей вправе их затереть):

```c
/* Ошибка: memcmp сравнивает и байты выравнивания между полями, равные структуры могут оказаться разными */
#include <stdbool.h>
#include <string.h>

typedef struct { char tag; int val; } rec;

bool rec_eq(const rec *a, const rec *b) { return memcmp(a, b, sizeof *a) == 0; }
```

Верно: сравнивать поля по очереди, `a->tag == b->tag && a->val == b->val`.

#### Подводные камни

- Память из `malloc` не обнулена; для массивов и структур бери `calloc` или арену, возвращающую нули ([аллокации](03-memory-ownership.md)).
- Структура, записанная в файл или сокет целиком, выносит байты выравнивания (утечка содержимого стека); сериализуй поля по одному ([системный уровень](11-system-io.md)).
- Буфер `char buf[N]`, заполненный частично, нельзя печатать как строку: нет завершающего нуля. Инициализируй `= {}` или записывай ноль явно.
- Предупреждения неполны: на примере `pick` Clang выдаёт `-Wsometimes-uninitialized`, а GCC 14 с `-Wall` молчит. Полагайся на инициализацию.

### Читай чужие байты через memcpy, а не через приведение указателя

Доступ к объекту через lvalue несовместимого типа нарушает strict aliasing, а указатель с более строгим выравниванием, чем у адреса, неопределён. Компилятор опирается на это правило: после записи через `float *` он не перечитывает `int`, прочитанный раньше, хотя указатели могли ссылаться на одну память. Исключение одно: через `char`, `signed char` и `unsigned char` можно читать байты любого объекта. Для переинтерпретации (биты `float`, поле заголовка по произвольному смещению) используй `memcpy`: при постоянной длине он превращается в одну инструкцию загрузки.

```c
#include <inttypes.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>

static_assert(sizeof(float) == sizeof(uint32_t));

uint32_t float_bits(float f) {
    uint32_t u;
    memcpy(&u, &f, sizeof u);
    return u;
}

uint32_t load_u32(const void *p) {
    uint32_t v;
    memcpy(&v, p, sizeof v);
    return v;
}

int main(void) {
    printf("%08" PRIx32 "\n", float_bits(1.0f)); /* вывод: 3f800000 */
    uint32_t want = 0x01020304;
    unsigned char raw[5] = {0};
    memcpy(raw + 1, &want, sizeof want);
    printf("%d\n", load_u32(raw + 1) == want); /* вывод: 1 */
    return 0;
}
```

Две типичные ошибки: приведение указателя на несовместимый тип и указатель на неверно выровненный адрес. Вторая ошибка ловится UBSan, первая санитайзерами не ловится вообще.

```c
/* Ошибка: чтение float через lvalue типа uint32_t нарушает strict aliasing */
#include <stdint.h>

uint32_t float_bits(float f) { return *(uint32_t *)&f; }
```

```c
/* Ошибка: UB, указатель на uint32_t по нечётному адресу */
#include <stdint.h>
#include <stdio.h>

int main(int argc, char **argv) {
    (void)argv;
    unsigned char buf[8] = {1, 2, 3, 4, 5, 6, 7, 8};
    uint32_t *p = (uint32_t *)(buf + argc);
    printf("%u\n", *p);
    return 0;
}
```

Не каждая комбинация байтов является значением типа: для `bool` допустимы только 0 и 1, и чтение иного значения неопределено (ловит UBSan).

```c
/* Ошибка: UB, в bool скопировано значение 2 */
#include <stdbool.h>
#include <stdio.h>
#include <string.h>

int main(int argc, char **argv) {
    (void)argv;
    unsigned char byte = (unsigned char)(argc + 1);
    bool b;
    memcpy(&b, &byte, 1);
    puts(b ? "да" : "нет");
    return 0;
}
```

#### Подводные камни

- Чтение другого члена `union` в C допустимо (байты переинтерпретируются), но основной путь всё же `memcpy`: он не зависит от того, какой член записан последним, и работает для произвольных смещений в буфере.
- Недопустимые представления: `bool` из внешних данных получай сравнением (`byte != 0`), а не копированием байта (пример выше).
- Буфер под структуру выделяй с выравниванием типа: `alignas(rec) unsigned char buf[sizeof(rec)]`, а выделения из `malloc` и арены уже выровнены ([аллокации](03-memory-ownership.md)). Приведение `char *` к `rec *` без этого неопределено при неверном адресе.
- `memcpy` даёт порядок байтов хоста. Для протоколов собирай значения побайтовыми сдвигами, как в `load_be32` выше ([двоичные протоколы](11-system-io.md)).
- `-fno-strict-aliasing` убирает следствия нарушения, но не само нарушение, и скрывает его от проверок ([инструменты сборки](01-toolchain.md)).

### Не храни адрес объекта, который кончился раньше указателя

Использование указателя на объект после конца его времени жизни неопределено, а на практике память уже отдана другому. Время жизни ограничивают блок для локальной переменной и составного литерала, полное выражение для временного значения, вызов `free` для выделенного блока.

Для коротких результатов возвращай структуру с массивом внутри по значению (`label make_label(int id)`): она принадлежит вызывающему и не требует ни статического буфера, ни аллокации. Временный объект из такого вызова живёт до конца полного выражения, поэтому `puts(make_label(8).s)` корректен.

Адрес локальной переменной, пережившей блок, ловит ASan (use-after-scope):

```c
/* Ошибка: UB, указатель на локальный массив использован после выхода из блока */
#include <stdio.h>

int main(int argc, char **argv) {
    (void)argv;
    int *p = nullptr;
    if (argc > 0) {
        int x[3] = {1, 2, 3};
        p = x;
    }
    printf("%d\n", p[1]);
    return 0;
}
```

Составной литерал и временный объект ведут себя так же, но санитайзеры их не всегда замечают:

```c
/* Ошибка: адреса составного литерала и временного массива сохранены за пределы их времени жизни */
#include <stdio.h>

typedef struct { char s[16]; } label;

label make_label(int id);

int main(void) {
    int *p;
    {
        p = (int[]){7, 8, 9};
    }
    const char *s = make_label(8).s;
    printf("%d %s\n", p[1], s);
    return 0;
}
```

#### Подводные камни

- Указатели на элементы динамического массива недействительны после `realloc` и роста контейнера; храни индексы, а не адреса ([аллокации](03-memory-ownership.md)).
- Возврат адреса локальной переменной компилятор обычно предупреждает; адрес, сохранённый в структуру или переданный наружу через out-параметр, он не отслеживает.
- Составной литерал в теле цикла живёт до конца итерации: адрес из него нельзя накапливать в список за пределами тела.

## Оптимизатор и санитайзеры

### Считай, что оптимизатор рассматривает неопределённое поведение как невозможное

Компилятор не обязан сохранять поведение программы с UB, и он выводит из каждого неопределённого действия доказательство, что оно не происходит. Отсюда типичные исчезновения кода; на `-O0` они часто не видны, и «работало» ничего не гарантирует. На `-O2` GCC 14 и Clang 19 удаляют проверку ниже.

```c
/* Ошибка: проверка p после разыменования, оптимизатор считает её лишней и удаляет */
int first(int *p) {
    int v = *p;
    if (!p) return -1;
    return v;
}
```

Разыменование выше доказывает для компилятора, что `p` не `nullptr`. Так же работает проверка переполнения после операции: для знакового `x` условие `x + 1 < x` превращается в константу `false` (при `-fwrapv` она снова вычисляется).

Менее очевидный пример касается стандартных функций: `memcpy`, `memmove` и `memcmp` требуют допустимых указателей даже при нулевой длине, поэтому пустой срез с `nullptr` нельзя передавать без проверки длины. После такого вызова компилятор вправе считать указатель ненулевым.

```c
/* Ошибка: UB, memcpy получил nullptr при нулевой длине */
#include <stddef.h>
#include <string.h>

void copy_bytes(void *dst, const void *src, size_t n) { memcpy(dst, src, n); }

int main(void) {
    char dst[4];
    copy_bytes(dst, nullptr, 0);
    return 0;
}
```

Верно: `if (n) memcpy(dst, src, n);`.

Цикл без наблюдаемых эффектов (ввод-вывод, `volatile`, атомарные операции) компилятор вправе считать завершающимся: Clang удаляет такой цикл целиком, GCC читает флаг один раз и зацикливается навсегда.

```c
/* Ошибка: ожидание флага без volatile и atomic, цикл выбрасывается или читает flag один раз */
int flag;

void wait_flag(void) {
    while (!flag) {
    }
}
```

Для флага из обработчика сигнала нужен `volatile sig_atomic_t`, для флага между потоками `atomic_bool` ([потоки](10-concurrency.md)).

Порядок вычисления аргументов функции и элементов списка инициализации не определён: Clang печатает `1 2`, GCC `2 1`.

```c
/* Ошибка: порядок вычисления аргументов не определён, результат зависит от компилятора */
#include <stdio.h>

static int c;
static int next(void) { return ++c; }

int main(void) {
    printf("%d %d\n", next(), next());
    return 0;
}
```

#### Подводные камни

- `a[i] = i++` и `i = i++ + 1` изменяют и читают одну переменную без упорядочения: неопределённое поведение (ловят `-Wsequence-point` и `-Wunsequenced`). Упорядочены только `&&`, `||`, `?:` и запятая.
- Цикл `for (int i = 0; i <= n; i++)` при `n == INT_MAX` не завершается, а оптимизатор вправе считать, что `i` не переполнится; используй `size_t` или строгое условие.
- Аргумент макроса подставляется столько раз, сколько он встречается в теле: `MAX(i++, j)` может увеличить `i` дважды ([контейнеры и макросы](09-containers-and-generics.md)).
- Запись в объект, объявленный `const`, и в строковый литерал (`char *s = "abc"; s[0] = 'x';`) неопределена; для изменяемой строки пиши `char s[] = "abc";`. Одинаковые литералы вправе делить один адрес, поэтому сравнивай содержимое, а не указатели на них.
- Управление не должно доходить до конца функции с не-`void` результатом: если вызывающий использует значение, поведение неопределено; `-Wreturn-type` из `-Wall` на Clang и GCC это ловит.
- Отсутствие сбоя на `-O0` ничего не доказывает: программа с UB некорректна при любом уровне оптимизации.

### Лови неопределённое поведение санитайзерами и держи в тестах

Неопределённое поведение проявляется только на выполненном пути, поэтому тестовую сборку собирай с ASan и UBSan и `-fno-sanitize-recover=all` (флаги, набор проверок и CI: [инструменты сборки](01-toolchain.md)). Чтение неинициализированной памяти ловит только MSan на Clang, усечение и смену знака в неявных преобразованиях `-fsanitize=implicit-conversion` (тоже Clang).

#### Подводные камни

- Санитайзер не видит нарушения strict aliasing, порядок вычисления, выброшенные циклы и проверки, потому что это решения компилятора, а не события во время выполнения; их находят чтением кода и предупреждениями.
- Флаги `-fwrapv`, `-fno-strict-aliasing` и `-fno-delete-null-pointer-checks` определяют поведение, которое иначе было бы неопределённым, и прячут ошибку от санитайзера: тестовую сборку держи без них.
- Покрытие определяется тестами: санитайзер проверяет только выполненные пути, поэтому его сочетают с фаззингом ([тестирование](07-testing-and-debugging.md)).

## Коротко

### Не сравнивай числа с плавающей точкой на равенство

Результат арифметики `double` округляется, `0.1 + 0.2` не равно `0.3`, а `NaN` не равен даже себе. Сравнивай с допуском (абсолютным около нуля, относительным для больших значений), а на `NaN` проверяй `isnan`. Флаг `-ffast-math` разрешает компилятору считать, что `NaN` и бесконечностей нет, и переставлять операции как ассоциативные: проверка `isnan` превращается в `0`, а порядок сложения может измениться, а с ним и результат. Деньги не храни во `float` и `double`: считай в целых минимальных единицах (`int64_t` копеек) с проверкой через `ckd_*`.

### Не обещай restrict, если не уверен

Квалификатор `restrict` сообщает компилятору, что через этот указатель объект не пересекается с обращениями через другие указатели; нарушить обещание значит получить неопределённое поведение, а выигрыш бывает только в горячих циклах. Подробности и измерения в [главе про производительность](13-performance.md).

### Используй nullptr, bool, constexpr, typeof и auto из C23

`nullptr` имеет собственный тип и однозначно обозначает нулевой указатель; `bool`, `true`, `false` стали ключевыми словами; `constexpr` объявляет объект-константу, пригодную как размер массива без VLA; `typeof(выражение)` даёт тип выражения; `auto` выводит тип объекта из инициализатора.

```c
#include <stdio.h>

constexpr int max_items = 4;

int main(void) {
    int items[max_items] = {};
    auto n = sizeof items / sizeof items[0];
    typeof(n) m = 2;
    const char *p = nullptr;
    bool ok = p == nullptr && m < n;
    printf("%zu %d\n", n, ok); /* вывод: 4 1 */
    return 0;
}
```

Ловушка `auto`: `auto i = 0;` имеет тип `int`, а не `size_t`, поэтому сравнение со `size_t` приводит к проблемам знаковости из практики про выбор типов; тип счётчика задавай явно.

### Фиксируй предположения о размерах через static_assert

Проверка при компиляции ловит неверный размер структуры или смещение поля до запуска; сообщение в C23 необязательно.

```c
#include <stddef.h>
#include <stdint.h>

typedef struct { uint32_t len; uint16_t kind, flags; } hdr;

static_assert(sizeof(hdr) == 8);
static_assert(offsetof(hdr, kind) == 4, "формат заголовка");
```

### Инициализируй по именам полей и индексам

Именованные инициализаторы (`{.host = "db", .port = 5432}`, `{[2] = "two"}`) устойчивы к перестановке полей: непоименованные поля и элементы равны нулю, а порядок не важен. Составной литерал `(тип){...}` создаёт безымянный объект и удобен для передачи параметров по адресу: `show(&(opts){.port = 80})`; живёт он до конца блока (см. практику про время жизни).

### Применяй unreachable() только при доказательстве

Макрос `unreachable()` из `<stddef.h>` (C23; Clang 19, Clang 20, GCC 14) сообщает оптимизатору, что управление сюда не придёт, и при ошибке даёт неопределённое поведение. Допустим там, где недостижимость следует из предыдущей проверки или маски; для «этого не должно случиться» используй `assert` или обработку ошибки ([ошибки](04-errors-and-cleanup.md)).

```c
#include <stddef.h>

int quarter_len(unsigned x) {
    switch (x & 3) {
    case 0: return 5;
    case 1: return 6;
    case 2: return 7;
    case 3: return 8;
    default: unreachable();
    }
}
```

### Задавай константы и форматы типов с фиксированной шириной макросами

Суффикс-макросы `INT32_C`, `UINT64_C` задают тип литерала, `UINT32_MAX`, `INT64_MIN` и (C23) `UINT32_WIDTH` дают пределы и ширину, а `PRIu64`, `PRId64` и `SCNu64` из `<inttypes.h>` подставляют правильный спецификатор формата; для `size_t` и `ptrdiff_t` есть `%zu` и `%td`. В C23 есть двоичные литералы (`0b1010`) и разделитель разрядов (`1'000'000`).

```c
#include <inttypes.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

int main(void) {
    uint64_t big = UINT64_C(1) << 40;
    printf("%" PRIu64 "\n", big); /* вывод: 1099511627776 */
    printf("%d\n", UINT32_WIDTH); /* вывод: 32 */
    printf("%zu %td\n", sizeof big, (ptrdiff_t)-1); /* вывод: 8 -1 */
    return 0;
}
```

## Что ещё стоит знать

Тип `_BitInt(N)` (GCC 14 на x86-64, Clang 19 и 20; суффикс литерала `wb`) задаёт целое произвольной ширины без продвижения в `int`, но не допускается в `ckd_*`.

Заголовок `<stdbit.h>` (glibc 2.39) даёт `stdc_count_ones`, `stdc_leading_zeros` и родственные операции над битами беззнаковых типов вместо ручных циклов и встроенных функций компилятора.

Тип `char8_t` из `<uchar.h>` и литералы `u8'a'`, `u8"..."` (C23) предназначены для кодовых единиц UTF-8; литерал `u8"..."` теперь имеет тип массива `char8_t`, и присваивание его `const char *` даёт предупреждение `-Wpointer-sign` на всех трёх компиляторах.

Зарезервированные идентификаторы (ведущее подчёркивание с заглавной буквой, внешние имена вида `strxxx`, суффикс `_t`) для своих имён не используют; перечень в практике про имена ([модули и API](06-api-and-modules.md)).
