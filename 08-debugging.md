# Отладка

## Сборка и символы

### Собирай для отладки и храни символы релиза отдельным файлом

Отладчику нужны строки и имена (`-g`, `-fno-omit-frame-pointer`: см. [сборка](01-toolchain.md)), но не оптимизации, из-за которых переменные исчезают, поэтому отладочную сборку делают с `-O0` (видно всё) или `-Og` (оптимизации, мало вредящие отладке; часть значений всё равно может показываться как `<optimized out>`, а встроенные функции как `[inlined]`). Релиз отлаживают теми же символами: их отделяют от бинарника и хранят рядом с артефактом сборки.

```sh
cc -std=c23 -g -Og -ffile-prefix-map=$PWD=/src prog.c -o prog
objcopy --only-keep-debug prog prog.debug
objcopy --strip-debug --add-gnu-debuglink=prog.debug prog
readelf -n prog | grep 'Build ID'
```

Первая `objcopy` копирует символы в `prog.debug`, вторая убирает их из бинарника и записывает в него имя и контрольную сумму файла символов (`gnu_debuglink`). Идентификатор сборки (build-id, в Ubuntu компиляторы пишут его по умолчанию) однозначно связывает бинарник, дамп памяти и файл символов: символы кладут как `.build-id/ab/cdef....debug` под первыми двумя шестнадцатеричными цифрами. `-ffile-prefix-map` заменяет в символах путь сборки на `/src`, чтобы бинарник не выдавал каталоги машины сборки и собирался воспроизводимо. Серверы debuginfod раздают символы по build-id, и отладчик берёт их оттуда сам.

На машине отладки LLDB находит `prog.debug` рядом с `prog` по `gnu_debuglink`. Если файл лежит в другом месте, каталог с деревом `.build-id` задают до загрузки программы, а исходники сопоставляют по замене пути:

```sh
lldb -O 'settings set target.debug-file-search-paths /srv/symbols' ./prog
```

```text
(lldb) target symbols add /srv/symbols/prog.debug
(lldb) settings set target.source-map /src /home/me/project
```

#### Подводные камни

- Бинарник без символов: в стеке `main + 85` вместо `main at prog.c:17`. Добавь символы командой `target symbols add`, проверь build-id обоих файлов.
- Файл `prog.debug` пересобран после `gnu_debuglink`: контрольная сумма в `gnu_debuglink` расходится с файлом, и отладчик может его проигнорировать; символы и бинарник берут из одной сборки.
- Исходники лежат по другому пути: строки в стеке есть, а текста нет (или предупреждение о контрольной сумме файла); нужна `target.source-map`.
- Релизный `-O2` показывает `<optimized out>` и прыгающие строки. Воспроизводи в `-O0` или `-Og`; если ошибка пропала, это признак неопределённого поведения, а не повод отлаживать оптимизированный код.

## Основные операции

### Находи причину падения в LLDB: стек, кадр, значения и наблюдательная точка

Когда санитайзеры не включены или не видят порчу (ASan не замечает запись внутри объекта), отладчик показывает, где остановилась программа и кто изменил значение. В примере цикл с `<=` пишет пятый элемент в массив из четырёх и затирает соседнее поле `name`: UBSan с `array-bounds` поймал бы это, а в сборке без него остаётся отладчик.

```c
/* Ошибка: UB, запись за границу массива v перезаписывает соседнее поле */
#include <stdio.h>

typedef struct { int v[4]; const char *name; } vec;

static void fill(vec *s, int n) {
    for (int i = 0; i <= n; i++) s->v[i] = i * 10;
}

static void report(const vec *s) {
    printf("%s: %d\n", s->name, s->v[1]);
}

int main(void) {
    vec s = {.name = "squares"};
    fill(&s, 4);
    report(&s);
}
```

Без санитайзера программа падает с `SIGSEGV` в `printf`. Бинарник отладчика в Ubuntu называется `lldb-20` (суффикс версии), ниже он записан как `lldb`. Опция `-b` запускает отладчик без диалога, `-o` задаёт команды по порядку, `-k` команды после остановки по сигналу (подробнее в разделе про пакетный режим).

```sh
cc -std=c23 -g -O0 crash.c -o crash
lldb -b -o run -k bt -k 'frame select 4' -k 'frame variable *s' -k 'quit 1' ./crash
```

```text
* thread #1, name = 'crash', stop reason = signal SIGSEGV: address not mapped to object (fault address=0x...)
  * frame #0: 0x... libc.so.6`___lldb_unnamed_symbol4483 + 29
    frame #3: 0x... libc.so.6`_IO_printf + 179
    frame #4: 0x... crash`report(s=0x...) at crash.c:11:5
    frame #5: 0x... crash`main at crash.c:17:5
frame #4: 0x... crash`report(s=0x...) at crash.c:11:5
-> 11  	    printf("%s: %d\n", s->name, s->v[1]);
(const vec) *s = {
  v = ([0] = 0, [1] = 10, [2] = 20, [3] = 30)
  name = 0x0000555500000028 ""
}
```

Падение случилось внутри libc, поэтому нужный кадр приложения выбирают командой `frame select N` (или `up`). Указатель `name` равен `0x...28`: младшие четыре байта дают `40` (`4 * 10`), то есть в поле-указатель записали число. Кто именно, покажет наблюдательная точка: она останавливает программу при записи по адресу.

```sh
lldb -b -o 'breakpoint set -n main' -o run -o next -o 'watchpoint set variable s.name' -o continue -o bt ./crash
```

```text
Watchpoint 1 hit:
old value: 0x...6004
new value: 0x...0028
* thread #1, name = 'crash', stop reason = watchpoint 1
    frame #0: 0x... crash`fill(s=0x..., n=4) at crash.c:7:30
-> 7   	    for (int i = 0; i <= n; i++) s->v[i] = i * 10;
```

`watchpoint set variable s.name` следит за адресом поля (восемь байт), а не за именем; `next` перед ней проходит инициализацию, иначе точка сработает на ней. Остановка в `fill` при `i = 4` показывает границу.

`frame variable` читает переменные прямо из отладочной информации: быстро, не выполняет код программы и показывает структуры и массивы целиком. `expr` компилирует выражение и умеет арифметику, присваивание и вызовы функций программы, но может изменить состояние процесса. В дампе памяти работает только чтение: вызвать функцию нельзя.

| Действие | LLDB | gdb |
| --- | --- | --- |
| Присоединиться к процессу | `lldb -p PID` | `gdb -p PID` |
| Открыть дамп памяти | `lldb -c core ./prog` | `gdb ./prog core` |
| Точка останова на функции или строке | `breakpoint set -n fill`, `b crash.c:7` | `break fill`, `break crash.c:7` |
| Условная точка останова | `breakpoint set -n fill -c 'n==4'` | `break fill if n==4` |
| Наблюдательная точка | `watchpoint set variable s.name` | `watch -l s.name` |
| Стек одного и всех потоков | `bt`, `bt all` | `bt`, `thread apply all bt` |
| Выбрать кадр | `frame select 4`, `up`, `down` | `frame 4`, `up`, `down` |
| Локальные переменные | `frame variable` (`v`) | `info locals` |
| Вычислить выражение | `expr s->v[1]` (`p`) | `print s->v[1]` |
| Список и выбор потока | `thread list`, `thread select 2` | `info threads`, `thread 2` |
| Сохранить дамп живого процесса | `process save-core file` | `gcore file` |
| Не останавливаться на сигнале | `process handle SIGPIPE --stop false` | `handle SIGPIPE nostop` |

#### Подводные камни

- Условие точки останова проверяет отладчик на каждом попадании; на горячей функции программа заметно замедляется. Условие можно вписать в сам код (`if (n == 4) DEBUG_BREAK();`, см. ниже).
- Аппаратных наблюдательных точек мало (на x86-64 четыре); наблюдай за одним полем, а не за структурой.

## Код, удобный для отладки

### Пиши функции-дампы, давай значениям имена и сохраняй имена потоков

Отладчик показывает только то, что есть в отладочной информации, поэтому структуры сложной формы удобнее печатать функцией, которую вызывают из `expr`. Дамп ставят рядом с типом и помечают `__attribute__((used))`, иначе оптимизатор может убрать «неиспользуемую» функцию.

```c
#define _GNU_SOURCE
#include <pthread.h>
#include <signal.h>
#include <stdio.h>

typedef struct { const char *ptr; size_t len; } str;
enum { MAX_ITEMS = 8 };
typedef enum { ST_IDLE, ST_BUSY, ST_DONE } state;
typedef struct { str items[MAX_ITEMS]; int count; state st; } list;

__attribute__((used)) void list_dump(const list *l) {
    fprintf(stderr, "list state=%d count=%d\n", (int)l->st, l->count);
    for (int i = 0; i < l->count; i++)
        fprintf(stderr, "  [%d] \"%.*s\"\n", i, (int)l->items[i].len, l->items[i].ptr);
}

#if __has_builtin(__builtin_debugtrap)
#define DEBUG_BREAK() __builtin_debugtrap()
#else
#define DEBUG_BREAK() raise(SIGTRAP)
#endif

void list_check(const list *l) {
    if (l->count > MAX_ITEMS) DEBUG_BREAK();
}

void worker_start(void) {
    pthread_setname_np(pthread_self(), "net-worker");
}
```

В остановленном процессе дамп вызывают выражением, в выводе виден результат с учётом `len`, чего не умеют строки-сводки (см. раздел «Коротко»):

```text
(lldb) frame select 3
(lldb) expr list_dump(&l)
list state=1 count=2
  [0] "alpha"
  [1] "beta"
```

`DEBUG_BREAK` останавливает процесс на месте, только если он под отладчиком; без него процесс завершается по `SIGTRAP` (код 133) и оставляет дамп. `__builtin_debugtrap` есть в Clang, у GCC 14 его нет, поэтому второй ветвью стоит `raise(SIGTRAP)`. Имя потока (до 15 символов) видно в `thread list` и `bt all` вместо номера. Состояния и константы описывай `enum`: `frame variable` печатает `ST_BUSY`, а не `1` (`#define`-макросы отладчик не видит даже при `-g3`, и `expr LIMIT` не сработает).

#### Подводные камни

- Дамп памяти без живого процесса: `expr list_dump(&l)` в дампе даёт `Can't evaluate the expression without a running target`. Читай значения через `frame variable` и `expr` без вызовов, а для сложных структур держи дамп и в виде читаемых полей.
- Дамп пишет в `stderr`: он не буферизован, и текст появляется сразу, а не при сбросе буфера `stdout`.
- Функция-дамп не должна изменять состояние и брать блокировки: при вызове из отладчика другие потоки остановлены, и захват чужого мьютекса повесит отладчик.
- Имена перечислений в `expr` без приведения типа не работают: `expr MODE_FAST` даёт `use of undeclared identifier`, а `expr (mode)1` печатает `MODE_FAST`.

## Пакетный режим и дампы

### Запускай отладчик в CI в пакетном режиме и не теряй код возврата теста

Тест, упавший на сервере сборки, нельзя повторить руками, поэтому стеки всех потоков снимают в момент падения: `lldb -b -o run -k 'bt all' -k 'quit 1' ./test`. Здесь `-b` включает пакетный режим, `-o run` запускает программу, а `-k` задаёт команды, которые выполняются только если программа остановилась по сигналу; после такой остановки остальные `-o` пропускаются (поэтому стек просят через `-k`, а не `-o`). `quit 1` возвращает код 1 вместо 0.

Код возврата отладчика не равен коду теста. Проверено запуском:

| Тест | Код возврата `lldb -b -o run -k ... -k 'quit 1'` |
| --- | --- |
| Завершился с кодом 0 | 0 |
| Завершился с кодом 3 без падения | 0 (провал теста не виден) |
| Упал по сигналу (`abort`) | 1 (из `quit 1`; без него 0) |

Поэтому голая команда в CI скрывает провал теста с ненулевым кодом. Надёжный рецепт: сначала обычный запуск, отладчик только для диагностики и с сохранением исходного кода возврата.

```sh
./test || { rc=$?; lldb -b -o run -k 'bt all' -k 'quit 1' ./test; exit $rc; }
```

Проверено: успешный тест даёт 0, тест с кодом 3 даёт 3, тест, упавший по `abort`, даёт 134. Плата за рецепт: упавший тест запускается второй раз, поэтому для редких гонок снимай дамп (см. ниже).

#### Подводные камни

- Зависший тест: отладчик ждёт вечно, и задачу CI снимает только общий таймаут. Заводи в тест собственный сторож (как `abort()` по таймауту в примере про взаимоблокировку ниже): тогда `-k` покажет стеки.
- В контейнере ptrace может быть запрещён профилем безопасности; образ книги запускается с `--security-opt seccomp=unconfined`, и отладчик в нём работает.
- Вывод отладчика смешивается с выводом теста: пиши его в отдельный файл и сохраняй как артефакт сборки.

### Разбирай падение по дампу памяти

Дамп содержит память и регистры процесса в момент падения, поэтому позволяет разобрать то, что не воспроизвести. `ulimit -c unlimited` разрешает запись дампа; куда он попадёт, говорит `/proc/sys/kernel/core_pattern`: шаблон имени файла или команда после `|` (тогда `ulimit -c` не действует, а дамп получает программа-сборщик). В системах с systemd сборщик сохраняет дамп, `coredumpctl list` показывает список, а `coredumpctl dump -o core` извлекает файл. Дамп открывают как остановленную программу, без `run`:

```sh
lldb -c core ./crash
```

Дальше те же `bt`, `frame select`, `frame variable`. Для живого процесса дамп снимают `gcore PID` (из gdb) или командой отладчика `process save-core -s full file`: стиль по умолчанию сохраняет только изменённую память, а `full` включает всё, что нужно при открытии на другой машине. Бинарник обязан быть тот же, из которого получен дамп; для релиза к нему добавляют `prog.debug`, лежащий рядом или подключённый `target symbols add` (проверено на дампе: без символов стек даёт `main + 209`, с ними `main at dump_main.c:9:5`).

#### Подводные камни

- Дамп не создаётся: `ulimit -c` равен `0` или `core_pattern` направляет его в программу, которая его отбросила. Проверь оба значения.
- Дамп и бинарник из разных сборок: стек и значения бессмысленны; сохраняй бинарник и символы рядом с дампом и называй их по build-id.
- Дамп открывают на другой машине: версии библиотек (`libc`) различаются, стеки внутри них неверны. Сохраняй дамп со стилем `full` или открывай в образе, с которого он снят.
- Дамп содержит память процесса целиком, включая ключи и пароли: храни с теми же правами доступа, что и данные, и не прикладывай к открытым задачам.

## Потоки

### Ищи взаимоблокировку по стекам всех потоков и владельцу мьютекса

Зависшая программа не падает и не оставляет следов, но стеки всех потоков показывают, кто где ждёт, а мьютекс glibc хранит идентификатор потока-владельца в поле `__data.__owner`. Пример намеренно вешает два потока, пока `main` не сработает как сторож: `pthread_timedjoin_np` с таймаутом вызывает `abort()`, и отладчик получает остановку с живыми потоками. Барьер гарантирует, что оба мьютекса уже заняты до второй блокировки: зависание детерминированно, а не зависит от планировщика.

```c
/* Ошибка: потоки берут мьютексы в разном порядке, взаимоблокировка */
#define _GNU_SOURCE
#include <pthread.h>
#include <stdlib.h>
#include <time.h>

static pthread_mutex_t lock_a = PTHREAD_MUTEX_INITIALIZER;
static pthread_mutex_t lock_b = PTHREAD_MUTEX_INITIALIZER;
static pthread_barrier_t both_held;

static void *take(pthread_mutex_t *first, pthread_mutex_t *second) {
    pthread_mutex_lock(first);
    pthread_barrier_wait(&both_held);
    pthread_mutex_lock(second);
    return nullptr;
}

static void *worker_ab(void *arg) {
    (void)arg;
    pthread_setname_np(pthread_self(), "worker-ab");
    return take(&lock_a, &lock_b);
}

static void *worker_ba(void *arg) {
    (void)arg;
    pthread_setname_np(pthread_self(), "worker-ba");
    return take(&lock_b, &lock_a);
}

int main(void) {
    pthread_barrier_init(&both_held, nullptr, 2);
    pthread_t ab, ba;
    pthread_create(&ab, nullptr, worker_ab, nullptr);
    pthread_create(&ba, nullptr, worker_ba, nullptr);
    struct timespec limit;
    clock_gettime(CLOCK_REALTIME, &limit);
    limit.tv_sec += 2;
    if (pthread_timedjoin_np(ab, nullptr, &limit) != 0) abort(); /* сторож */
    pthread_join(ba, nullptr);
}
```

```sh
cc -std=gnu23 -g -O0 -pthread dl.c -o dl
lldb -b -o run -k 'thread backtrace all' -k 'expr lock_a.__data.__owner' -k 'expr lock_b.__data.__owner' -k 'thread list' -k 'quit 1' ./dl
```

```text
  thread #2, name = 'worker-ab'
    frame #1: 0x... libc.so.6`pthread_mutex_lock + 273
    frame #2: 0x... dl`take(first=0x...088, second=0x...0b0) at dl.c:14:5
  thread #3, name = 'worker-ba'
    frame #1: 0x... libc.so.6`pthread_mutex_lock + 273
    frame #2: 0x... dl`take(first=0x...0b0, second=0x...088) at dl.c:14:5
(int) $0 = 26
(int) $1 = 27
  thread #2: tid = 26, ... name = 'worker-ab'
  thread #3: tid = 27, ... name = 'worker-ba'
```

Оба потока стоят в `pthread_mutex_lock` внутри `take`, причём `first` одного равен `second` другого. Владелец `lock_a` (26) это `worker-ab`, владелец `lock_b` (27) это `worker-ba`: `worker-ab` ждёт мьютекс потока `worker-ba` и наоборот, цикл замкнут. Номера потоков при каждом запуске разные, сверяются только пары. Лечение: единый порядок захвата для всех путей (см. [потоки](10-concurrency.md)).

#### Подводные камни

- Поле `__data.__owner` принадлежит внутреннему устройству `pthread_mutex_t` в glibc и годится как диагностика, а не как интерфейс программы; проверено на glibc 2.39 для обычного мьютекса.
- В `bt all` ждущие потоки показывают внутренний кадр libc без имени: ищи ближайший кадр с `pthread_mutex_lock`, `pthread_cond_wait` или `futex`.
- Остановка отладчиком меняет тайминги: гонка, пропавшая под отладчиком, ищется в ThreadSanitizer ([сборка](01-toolchain.md)), а не в LLDB.

## Коротко

### Подключай строки-сводки типов файлом команд

Сводка (`type summary add`) учит отладчик печатать значение типа в одну строку вместо поля за полем. Команды кладут в файл и подключают `command source file` (или из `~/.lldbinit`, чтобы они действовали во всех сессиях).

```text
type summary add str --summary-string "${var.ptr} len=${var.len}"
```

После `command source str.lldb` значение `str s = {"beta-extra", 4}` печатается как `"beta-extra" len=4`. Но сводка не может учитывать `len`: она читает указатель как строку до нулевого байта, а диапазон `${var.ptr[0-3]}` принимает только константы, не поле структуры (проверено запуском: срез длины 4 печатает все десять символов). Если нужна точная печать среза, используй функцию-дамп из практики выше.

### SB API: отладчик как библиотека

Весь LLDB построен на объектном API с префиксом `SB` (scripting bridge): `SBDebugger` создаёт сессию, `SBTarget` описывает программу, `SBProcess` запущенный процесс, `SBThread` и `SBFrame` потоки и кадры, `SBValue` значения переменных. Привязки есть для Python и C++, а командная строка `lldb` сама написана поверх этого API. На нём строят форматтеры типов с логикой (например печать среза по длине), автоматический анализ падений (скрипт открывает дамп, собирает стеки и значения и отправляет отчёт), собственные команды и инструменты. Для разового разбора хватает команд, а SB API нужен, когда одну и ту же процедуру нужно повторять на сотнях дампов.

### DAP: отладчик в редакторе

Протокол отладочного адаптера (Debug Adapter Protocol, DAP) описывает обмен между редактором и отладчиком: редактор отправляет запросы (точки останова, шаг, значения), адаптер отвечает событиями. `lldb-dap` входит в состав LLVM и подключает LLDB к любому редактору с поддержкой DAP, без привязки к конкретному. Конфигурация запуска задаётся полями: программа, аргументы, рабочий каталог, окружение, остановка на входе, команды инициализации (например `settings set target.source-map ...`), присоединение к процессу, открытие дампа, сопоставление путей. Те же настройки, что в `.lldbinit`, переносятся в эту конфигурацию, поэтому вручную проверенный рецепт запуска становится настройкой редактора.

## Что ещё стоит знать

LLDB по умолчанию отключает ASLR (`settings set target.disable-aslr false` его возвращает), поэтому ошибки, зависящие от случайных адресов, под отладчиком не воспроизводятся; он также останавливается на `SIGPIPE`, что для сетевых программ отключает `process handle SIGPIPE --stop false --notify false`. Присоединение к чужому процессу `lldb -p PID` при `kernel.yama.ptrace_scope = 1` (так в Ubuntu и в контейнере образа) завершается ошибкой, пока не запустить от root или не снять ограничение. Для удалённой и контейнерной отладки на цели запускают `lldb-server`, а на рабочей машине подключаются к нему. Отладчик rr записывает выполнение и позволяет шагать назад, что спасает от невоспроизводимых гонок. Valgrind остаётся инструментом из главы про [тесты](07-testing-and-debugging.md).
