# Проектирование интерфейсов и модулей

## Модуль

### Прячь устройство типа в .c и давай всем публичным именам один префикс

Заголовок является обещанием клиентам: всё, что в нём лежит, нельзя изменить, не сломав их код, поэтому в нём остаются только объявления. Тип делают непрозрачным (`struct buf` определена в `.c`, клиент держит лишь указатель), каждый публичный символ начинается с префикса модуля (`buf_`), всё остальное объявляют `static`. Заголовок самодостаточен: сам подключает всё, что нужно ему для компиляции, и защищён от повторного включения. Пара `buf_create`/`buf_destroy` следует правилам из [владения и жизненного цикла](04-memory-ownership.md).

```c
/* buf.h */
#ifndef BUF_H
#define BUF_H
#include <stddef.h>

#define BUF_API [[gnu::visibility("default")]]

typedef struct buf buf;

BUF_API buf *buf_create(void);
BUF_API void buf_destroy(buf *b);
BUF_API int buf_append(buf *b, const void *data, size_t n);
BUF_API const char *buf_data(const buf *b);
BUF_API size_t buf_len(const buf *b);
#endif
```

```c
/* buf.c */
#include "buf.h"
#include <errno.h>
#include <stdint.h>
#include <stdlib.h>
#include <string.h>

struct buf { char *data; size_t len, cap; };

buf *buf_create(void) { return calloc(1, sizeof(buf)); }

void buf_destroy(buf *b) {
    if (b) free(b->data);
    free(b);
}

static int grow(buf *b, size_t need) {
    if (need <= b->cap) return 0;
    size_t cap = b->cap ? b->cap : 16;
    while (cap < need) {
        if (cap > SIZE_MAX / 2) return -ENOMEM;
        cap *= 2;
    }
    char *p = realloc(b->data, cap);
    if (!p) return -ENOMEM;
    b->data = p;
    b->cap = cap;
    return 0;
}

int buf_append(buf *b, const void *data, size_t n) {
    if (n >= SIZE_MAX - b->len) return -ENOMEM;
    int rc = grow(b, b->len + n + 1); /* +1 под завершающий NUL */
    if (rc != 0) return rc;
    if (n) memcpy(b->data + b->len, data, n);
    b->len += n;
    b->data[b->len] = '\0';
    return 0;
}

const char *buf_data(const buf *b) { return b->data ? b->data : ""; }
size_t buf_len(const buf *b) { return b->len; }
```

```c
/* main.c */
#include "buf.h"
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    buf *b = buf_create();
    if (!b) abort();
    if (buf_append(b, "hello, ", 7) != 0 || buf_append(b, "world", 5) != 0) abort();
    printf("%zu %s\n", buf_len(b), buf_data(b)); /* вывод: 12 hello, world */
    buf_destroy(b);
}
```

Макрос `BUF_API` задаёт символу видимость `default` явно (атрибут понимают GCC и Clang), а флаг `-fvisibility=hidden` меняет умолчание для всех остальных символов на скрытое: наружу из разделяемой библиотеки выходят только объявленные с `BUF_API`. Сравнение на модуле с лишней функцией без `static`:

```sh
echo 'int buf_helper(int x) { return x + 1; }' > extra.c
cc -std=c23 -fPIC -shared buf.c extra.c -o libbuf.so
nm -D --defined-only libbuf.so | awk '$2 == "T" { print $3 }'
cc -std=c23 -fPIC -shared -fvisibility=hidden buf.c extra.c -o libbuf.so
nm -D --defined-only libbuf.so | awk '$2 == "T" { print $3 }'
```

```text
buf_append
buf_create
buf_data
buf_destroy
buf_helper
buf_len
buf_append
buf_create
buf_data
buf_destroy
buf_len
```

Без флага наружу выходят все шесть функций, включая случайно забытую `buf_helper`, и клиент может начать ею пользоваться; с флагом остаются пять помеченных `BUF_API`. Самодостаточность заголовка проверяют компиляцией только его: `cc -std=c23 -fsyntax-only -x c buf.h` не должна давать ошибок.

#### Подводные камни

- Забытый `static` у внутренней функции. Символ с общим именем попадает в таблицу библиотеки и конфликтует с одноимённым символом программы; проверяй `nm` и собирай с `-fvisibility=hidden` (видимость действует только на `.so`; для статической библиотеки границу задают `static` и префиксы).
- Структура в публичном заголовке «ради `sizeof`» или быстрых полей. Клиенты начинают зависеть от раскладки, и любое изменение ломает их; если значение действительно должно жить у клиента на стеке, структуру делают публичной осознанно (см. практику про стабильность ABI).
- Заголовок рассчитывает на чужие `#include` или охранный макрос без привязки к проекту. Ошибка видна только в одном порядке включения, а два модуля с одинаковым именем файла молча отключают друг друга; проверяй заголовок отдельной компиляцией и добавляй имя проекта в макрос (`MYAPP_BUF_H`).

### Пиши контракт функции в комментарии и ставь [[nodiscard]]

Сигнатура описывает типы, но не говорит, кто освобождает результат, допустим ли `nullptr`, что остаётся после ошибки и как долго живёт возвращённый указатель, поэтому всё неочевидное записывают комментарием перед объявлением в заголовке: клиент читает именно его. Шаблон из пяти пунктов (пиши только то, что нельзя вывести из сигнатуры): что делает функция одной фразой, владение и допустимость `nullptr` для каждого указателя ([правило владения](04-memory-ownership.md)), возвращаемое значение и состояние объекта при ошибке ([схемы ошибок](05-errors-and-cleanup.md)), потокобезопасность, инвалидация указателей. Атрибут `[[nodiscard]]` ставят на функции, результат которых нельзя игнорировать: коды ошибок и всё, что возвращает владение (аллокаторы, `_create`); компилятор предупредит о потерянном результате.

```c
/* buf.h */
#ifndef BUF_H
#define BUF_H
#include <stddef.h>

#define BUF_API [[gnu::visibility("default")]]

typedef struct buf buf;

/* buf_create - создаёт пустой буфер.
 * Возврат: буфер во владении вызывающего (освободить buf_destroy) или nullptr при нехватке памяти (единственная причина отказа, поэтому `int *err` не нужен). */
[[nodiscard]] BUF_API buf *buf_create(void);

/* buf_destroy - освобождает буфер; допустим nullptr. Указатели из buf_data после вызова недействительны. */
BUF_API void buf_destroy(buf *b);

/* buf_append - добавляет n байт в конец буфера.
 * b: не nullptr, заимствуется. data: n байт, заимствуется; допустим nullptr при n == 0.
 * Возврат: 0 или -ENOMEM; при ошибке буфер не изменён.
 * Потоки: не потокобезопасна для одного буфера. Инвалидирует указатели на содержимое. */
[[nodiscard]] BUF_API int buf_append(buf *b, const void *data, size_t n);

/* buf_data - содержимое как C-строка (NUL в конце; байты NUL внутри возможны).
 * Результат принадлежит буферу и действителен до следующего buf_append или buf_destroy. */
BUF_API const char *buf_data(const buf *b);
BUF_API size_t buf_len(const buf *b);
#endif
```

Вызов `buf_append(b, "x", 1);` без проверки результата даёт предупреждение `-Wunused-result`. Осознанный отказ от результата пишут `(void)buf_append(...)` с комментарием, почему ошибка не важна. Родственная защита: управление не должно доходить до конца не-void функции без `return`; это ловит `-Wreturn-type` (входит в `-Wall`), а использование такого результата неопределено.

Атрибуты в публичном заголовке, который включают чужие программы, пишут в форме с двойным подчёркиванием: если клиент определил макрос `nodiscard` или `deprecated`, препроцессор перепишет обычную запись, а `[[__nodiscard__]]` равнозначна стандартной и защищена от подмены. `[[__deprecated__("use x_v2")]]` помечает устаревшую функцию с подсказкой; `[[__maybe_unused__]]` на параметре подавляет предупреждение о неиспользуемом параметре callback и нужна в определении в `.c`, а не в заголовке.

```c
#include <stddef.h>

[[__nodiscard__]] int stub_read(void *ctx, void *buf, size_t n);
[[__deprecated__("use stub_read")]] int stub_old(void *ctx);
```

Форма указателя в сигнатуре сообщает часть контракта без комментария. Один объект, не `nullptr`: параметр `const point p[static 1]` (или комментарий «не nullptr»). Коллекция известной длины: длина идёт первой, массив после неё, `const point pts[static n]`. Допускающий `nullptr`: обычный указатель и запись в контракте, что значит `nullptr`.

```c
#include <stddef.h>

typedef struct { int x, y; } point;

/* Один объект, не nullptr. */
int point_sum(const point p[static 1]) { return p->x + p->y; }

/* Коллекция: n объявлено до массива, n элементов, не nullptr. */
long points_sum(size_t n, const point pts[static n]) {
    long s = 0;
    for (size_t i = 0; i < n; i++) s += point_sum(&pts[i]);
    return s;
}

/* Допускающий nullptr: nullptr означает имя по умолчанию. */
const char *name_or_default(const char *name) { return name ? name : "default"; }
```

Запись `[static N]` обещает компилятору, что по указателю доступно не меньше `N` элементов, и он вправе предупредить о нарушении при вызове. Проверка на конкретных ошибках:

```c
/* Ошибка: вызовы нарушают предусловия параметров-массивов */
#include <stddef.h>

int sum4(const int a[static 4]);
int sum(size_t n, const int a[static n]);

int run(void) {
    int small[2] = {1, 2};
    return sum4(small) + sum(2, nullptr);
}
```

Clang сообщает `-Warray-bounds` (слишком короткий массив) и `-Wnonnull`; GCC 14 сообщает `-Wnonnull` и `-Wstringop-overread`.

#### Подводные камни

- Предупреждения нет, а нарушение есть. Это проверка на этапе компиляции, и только для видимых компилятору значений: `nullptr` из переменной и короткий массив неопределённой длины проходят молча, поведение при нарушении неопределено ([неопределённое поведение](03-types-and-ub.md)).
- Оптимизатор верит обещанию. Проверка `if (!a)` внутри функции с `a[static 1]` может быть удалена: на GCC 14 и Clang 19 при `-O2` функция `return a == nullptr;` с таким параметром возвращает 0 даже при вызове с `nullptr`. Для параметра, который могут передать как `nullptr`, `static` не пиши.
- Размер проверяют не везде. При длине, заданной параметром (`a[static n]`), Clang диагностирует только `nullptr`, а слишком короткий массив замечает лишь при константной длине в самом объявлении (`a[static 4]`); GCC проверяет оба случая.
- Параметр `a[static n]` является массивом переменной длины, и `-Wvla` на него срабатывает; если флаг включён в проекте, ограничься правилом против VLA на стеке.
- Контракт описывает реализацию («использует `realloc`»). Закрепляются детали, которые хотелось бы менять; в заголовке пиши «что и зачем», меняя поведение, правь комментарий в том же коммите.
- `[[nodiscard]]` на функциях, результат которых обычно игнорируют. Клиенты затыкают предупреждение приведением `(void)` повсюду, и сигнал теряет ценность.

## Данные и вызовы

### Проектируй тип так, чтобы {} был допустимым значением

Устройство и примеры нулевого состояния (нулевой указатель, нулевая длина, нулевой флаг, пары `_init`/`_clear` и `_create`/`_destroy`) разобраны в [разделе про владение](04-memory-ownership.md); здесь следствие для интерфейса: в контракте типа пишут «нулевое значение допустимо», тип без такого значения (непрозрачный) клиент получает только через `_create`, а каждую функцию типа прогоняют в тесте на `{}`. Поле, у которого разумное значение по умолчанию не ноль (порт 8080), превращает `{}` в тихо неверную настройку: храни «0 = по умолчанию» и подставляй значение при использовании, как в практике про структуру опций.

### Заменяй длинные списки параметров структурой опций

Позиционный список из пяти и более параметров нечитаем на месте вызова (`open(h, 0, 3000, 1, 0)`) и не расширяется без поломки каждого вызова. Структура с именованными полями, заполняемая designated initializers, читается на месте и допускает добавление полей; compound literal создаёт её прямо в вызове, а нули означают значения по умолчанию, так что структура заменяет и аргументы по умолчанию, которых в C нет. Значение `nullptr` вместо всей структуры означает «всё по умолчанию».

```c
#include <stdio.h>

typedef struct {
    const char *host; /* nullptr: "localhost" */
    int port;         /* 0: 8080 */
    int timeout_ms;   /* 0: 3000 */
    bool verbose;
} srv_opts;

/* srv_start - o == nullptr означает всё по умолчанию. o заимствуется только на время вызова. */
static int srv_start(const srv_opts *o) {
    srv_opts d = o ? *o : (srv_opts){};
    if (!d.host) d.host = "localhost";
    if (!d.port) d.port = 8080;
    if (!d.timeout_ms) d.timeout_ms = 3000;
    printf("%s:%d %d\n", d.host, d.port, d.timeout_ms);
    return 0;
}

int main(void) {
    srv_start(nullptr); /* вывод: localhost:8080 3000 */
    srv_start(&(srv_opts){.port = 9000, .verbose = true}); /* вывод: localhost:9000 3000 */
    srv_start(&(srv_opts){.host = "example.org", .timeout_ms = 500}); /* вывод: example.org:8080 500 */
}
```

Функция копирует структуру в локальную переменную и подставляет умолчания в копии: исходную она не меняет, а клиент не обязан заполнять всё.

#### Подводные камни

- Ноль как «по умолчанию» отнимает ноль как значение: `timeout_ms = 0` не может значить «не ждать». Выбери кодировку явно: отдельное значение (`-1`), отдельный флаг или перечисление.
- Позиционная инициализация `{"h", 1, 2}` ломается при вставке поля в середину. Документируй только именованную форму, новые поля добавляй в конец.
- Compound literal живёт до конца окружающего блока. Функция, которая сохраняет указатель на переданную структуру, получает висячий указатель; контракт требует копировать нужное во время вызова.
- Строки внутри опций заимствованы: если функция хранит `host`, она копирует его сама (правило [заимствования](04-memory-ownership.md)).
- Недопустимые значения (отрицательный порт) исправляются молча. Возвращай `-EINVAL`: тихая подстановка скрывает ошибку клиента.

### Принимай буфер от вызывающего и делай двухфазный вызов

Функция, которой нужен выходной буфер, не обязана выделять память: она принимает буфер и его ёмкость и возвращает размер, который понадобился бы для полного результата, как `snprintf`. Клиент сам решает, где взять память (стек, арена, куча), а функция не имеет пути отказа по памяти. Если размер неизвестен, вызов делают дважды: сначала с `nullptr` и нулевой ёмкостью, чтобы узнать размер, затем с буфером нужного размера.

```c
#include <stdio.h>
#include <stdlib.h>

/* hex_encode - пишет шестнадцатеричную запись n байт src в dst как C-строку.
 * Возврат: длина полной записи без NUL (2 * n), даже если dst мал; при cap <= длины запись
 * усечена, а при cap > 0 в dst всегда есть NUL. dst допустим nullptr только при cap == 0. */
size_t hex_encode(char *dst, size_t cap, const void *src, size_t n) {
    static const char digits[] = "0123456789abcdef";
    const unsigned char *p = src;
    size_t k = 0;
    while (k < n && 2 * k + 2 < cap) {
        dst[2 * k] = digits[p[k] >> 4];
        dst[2 * k + 1] = digits[p[k] & 15];
        k++;
    }
    if (cap) dst[2 * k] = '\0';
    return 2 * n;
}

int main(void) {
    const unsigned char data[] = {0xde, 0xad, 0xbe, 0xef};
    char small[6];
    size_t need = hex_encode(small, sizeof small, data, sizeof data);
    printf("%zu %s\n", need, small); /* вывод: 8 dead */
    char *out = malloc(hex_encode(nullptr, 0, data, sizeof data) + 1);
    if (!out) abort();
    hex_encode(out, need + 1, data, sizeof data);
    puts(out); /* вывод: deadbeef */
    free(out);
}
```

Результат `8` больше ёмкости `6`: запись усечена. Если результат должен пережить вызов и размер заранее неизвестен, функция принимает арену ([арены](04-memory-ownership.md)) или возвращает объект во владение вызывающего по схеме `_create`.

#### Подводные камни

- Усечение не замечено: клиент не сравнил результат с ёмкостью (`need >= cap`). Между двумя вызовами размер мог измениться; сверяй со вторым результатом.
- `dst == nullptr` при ненулевой ёмкости. Контракт обязан отличать его от `cap == 0` (в примере при `cap == 0` в `dst` не пишут); `memcpy` с `nullptr` при нулевой длине разобран в [неопределённом поведении](03-types-and-ub.md).
- Результат типа `size_t` не умеет сообщать об ошибках. Если у функции есть настоящие отказы, возвращай `int` по общей схеме, а размер отдавай через `size_t *need`.
- Размер результата вычисляется умножением (`2 * n`, `n + 1`) и может переполниться: проверяй через `ckd_mul` ([переполнение](03-types-and-ub.md)).

## Расширение и сопровождение

### Передавай callback вместе с user_data, а набор операций оформляй таблицей

Функция без состояния не знает, к чему обратиться из callback, поэтому рядом с указателем на функцию всегда передают `void *user_data`, который библиотека не читает и возвращает обратно как есть. Набор операций, которые варьируются (чтение, закрытие), собирают в структуру с указателями на функции, статическую и константную; объект хранит указатель на таблицу и свой контекст. Реализации подставляются без правки клиента (применения: [тесты](09-testing.md) и [внедрение зависимостей](21-patterns.md)). Контекст callback называют `user_data`, контекст таблицы `ctx`.

```c
#include <stdio.h>
#include <string.h>

typedef struct ops { int (*read)(void *ctx, void *buf, size_t n); void (*close)(void *ctx); } ops;
typedef struct stream { const ops *vt; void *ctx; } stream;

/* stream_read - читает до n байт (n <= INT_MAX).
 * Возврат: число прочитанных байт (0 - конец данных) или -E...; close может отсутствовать. */
static int stream_read(stream s, void *buf, size_t n) { return s.vt->read(s.ctx, buf, n); }

typedef struct { const char *p; size_t left; } mem_src;

static int mem_read(void *ctx, void *buf, size_t n) {
    mem_src *m = ctx; /* контекст приводится к своему типу внутри реализации */
    size_t k = n < m->left ? n : m->left;
    if (k) memcpy(buf, m->p, k);
    m->p += k;
    m->left -= k;
    return (int)k;
}

static const ops mem_ops = {.read = mem_read};

int main(void) {
    mem_src src = {"hello", 5};
    stream s = {&mem_ops, &src};
    char buf[4];
    int n = stream_read(s, buf, sizeof buf);
    printf("%d\n", n); /* вывод: 4 */
}
```

Возврат `read` продолжает общую схему: неотрицательное значение означает успех (здесь число байт), отрицательное означает `-E...`. Полный пример подмены таблицы в тесте и внедрения зависимостей дан в [паттернах](21-patterns.md). Callback без таблицы устроен так же: указатель на функцию и контекст.

```c
#include <stdio.h>

/* array_each - вызывает fn(user_data, a[i]) по порядку.
 * Ненулевой результат fn прерывает обход и возвращается. fn не должна менять a. */
static int array_each(const int *a, size_t n, int (*fn)(void *user_data, int x), void *user_data) {
    for (size_t i = 0; i < n; i++) {
        int rc = fn(user_data, a[i]);
        if (rc != 0) return rc;
    }
    return 0;
}

typedef struct { long sum; int limit; } acc;

static int add_until(void *user, int x) {
    acc *s = user;
    if (x > s->limit) return 1;
    s->sum += x;
    return 0;
}

int main(void) {
    const int a[] = {1, 2, 3, 50, 4};
    acc s = {.limit = 10};
    int rc = array_each(a, 5, add_until, &s);
    printf("%d %ld\n", rc, s.sum); /* вывод: 1 6 */
}
```

Вызов функции через указатель несовместимого типа имеет неопределённое поведение, даже если на вашей платформе «работает». Поэтому деструктор типа `void (*)(void *)` принимает `free` напрямую, а собственную функцию с типизированным параметром оборачивают адаптером, где приведение делается к указателю на данные, а не к типу функции.

```c
#include <stdlib.h>
#include <string.h>

typedef struct { void *items[4]; size_t len; void (*dtor)(void *); } owned;
typedef struct { char *name; } user;

static void user_destroy(user *u) {
    if (u) free(u->name);
    free(u);
}

/* Адаптер: сигнатура точно void(void *), приведение данных внутри. */
static void user_dtor(void *p) { user_destroy(p); }

static void owned_clear(owned *o) {
    for (size_t i = 0; i < o->len; i++)
        if (o->dtor) o->dtor(o->items[i]);
    *o = (owned){};
}

int main(void) {
    owned strs = {.dtor = free}, users = {.dtor = user_dtor};
    char *s = strdup("a");
    user *u = calloc(1, sizeof *u);
    if (!s || !u) abort();
    strs.items[strs.len++] = s;
    u->name = strdup("bob");
    if (!u->name) abort();
    users.items[users.len++] = u;
    owned_clear(&strs);
    owned_clear(&users);
}
```

Типичная ошибка: привести собственную функцию к типу деструктора.

```c
/* Ошибка: вызов функции через указатель несовместимого типа */
#include <stdlib.h>

typedef struct { char *name; } user;
static void user_destroy(user *u) { free(u->name); free(u); }

void run(void (*dtor)(void *), void *p) { dtor(p); }

void demo(user *u) { run((void (*)(void *))user_destroy, u); }
```

Это неопределённое поведение: тип `void (*)(user *)` несовместим с `void (*)(void *)`. Компилятор молчит, а Clang с `-fsanitize=undefined` (проверка `function`) сообщает `call to function ... through pointer to incorrect function type` при вызове; GCC 14 такой проверки не имеет.

#### Подводные камни

- Время жизни `user_data`. Указатель на локальную переменную, сохранённый для отложенного вызова, к моменту callback уже висит; в контракте регистрации пиши, сколько должен жить контекст.
- Контекст приводят не к тому типу, что передавали: неопределённое поведение без диагностики.
- Callback меняет объект, по которому идёт обход: инвалидация итерации; запрещай это в контракте.
- Необязательная операция в таблице оставлена `nullptr` и вызывается без проверки. Падение; либо проверяй (как `close` в примере), либо объяви операцию обязательной.
- Таблица не `const`. Её указатели можно перезаписать, а компилятор не может разместить таблицу в памяти только для чтения; пиши `static const ops`.
- Из какого потока вызывается callback и можно ли в нём вызывать функции той же библиотеки. Без записи в контракте клиент угадывает ([потоки](12-concurrency.md)).

### Передавай контекст вместо глобального состояния

Всё, что функция запоминает между вызовами или берёт «из окружающей среды» (статическая переменная, глобальный аллокатор, `exit` при ошибке), делает её непригодной для двух клиентов в одном процессе, для потоков и для тестов. Библиотечная функция не вызывает `exit` и `abort` (ошибка возвращается кодом, решение за приложением), не печатает в `stdout`/`stderr` (диагностика идёт через код ошибки или через callback из контекста), не меняет локаль, обработчики сигналов и `atexit`, не держит `static` локальных изменяемых переменных. Состояние живёт в объекте-контексте, который передаёт клиент; функция без состояния (результат зависит только от аргументов) безопасна для потоков по построению.

```c
/* Ошибка: библиотечная функция печатает, завершает процесс и держит общий буфер */
#include <stdio.h>
#include <stdlib.h>

const char *port_error(int code) {
    static char msg[64];
    snprintf(msg, sizeof msg, "bad port (code %d)", code);
    return msg;
}

int parse_port(const char *s) {
    char *end;
    long v = strtol(s, &end, 10);
    if (*end || v < 1 || v > 65535) {
        fprintf(stderr, "%s\n", port_error(1));
        exit(1);
    }
    return (int)v;
}
```

Исправленный вариант возвращает код и результат через out-параметр, ничего не печатает и не хранит; сообщение формирует вызывающий.

```c
#include <errno.h>
#include <stdlib.h>

/* parse_port - разбирает порт 1..65535 из строки только из цифр. Возврат: 0 или -EINVAL; результат в *out. */
[[nodiscard]] int parse_port(const char *s, int *out) {
    if (*s < '0' || *s > '9') return -EINVAL; /* strtol пропустил бы пробелы и знак */
    char *end;
    errno = 0;
    long v = strtol(s, &end, 10);
    if (errno != 0 || *end || v < 1 || v > 65535) return -EINVAL;
    *out = (int)v;
    return 0;
}
```

Остальные проверки разбора чисел описаны в [строках и буферах](06-strings-and-buffers.md).

Аллокатор внедряют как интерфейс: структура с функциями выделения и освобождения и контекстом, которую объект запоминает при создании. Нулевое значение структуры означает `malloc`/`free`, так что клиент, которому это не нужно, ничего не задаёт. Тот же приём подключает арену ([арены](04-memory-ownership.md): `alloc` выделяет из арены, `free` ничего не делает) и подменяет аллокатор в тесте для инжекции отказов ([тесты](09-testing.md)).

```c
#include <stdio.h>
#include <stdlib.h>

typedef struct allocator {
    void *(*alloc)(void *ctx, size_t size);
    void (*free)(void *ctx, void *p);
    void *ctx;
} allocator; /* {}: malloc и free */

static void *mem_alloc(const allocator *a, size_t n) { return a->alloc ? a->alloc(a->ctx, n) : malloc(n); }
static void mem_free(const allocator *a, void *p) { if (a->free) a->free(a->ctx, p); else free(p); }

typedef struct { int allocs, frees; } stats;
static void *counting_alloc(void *ctx, size_t n) { ((stats *)ctx)->allocs++; return malloc(n); }
static void counting_free(void *ctx, void *p) { if (p) ((stats *)ctx)->frees++; free(p); }

int main(void) {
    stats st = {};
    allocator a = {counting_alloc, counting_free, &st}; /* объект хранит его при создании */
    void *p = mem_alloc(&a, 16);
    if (!p) abort();
    mem_free(&a, p);
    printf("%d %d\n", st.allocs, st.frees); /* вывод: 1 1 */
}
```

Объект использует сохранённый аллокатор для всех операций над своей памятью: так блок всегда освобождается тем же аллокатором, которым выделен.

#### Подводные камни

- `static` переменная в функции или глобальная переменная модуля. Два клиента в одном процессе делят состояние, а при потоках получаются гонки ([потоки](12-concurrency.md)); состояние переносят в контекст.
- Функция печатает или завершает процесс. Приложение не может ни перехватить сообщение, ни откатить состояние; возвращай код, а диагностику отдавай через callback контекста.
- Глобальная функция `set_allocator()` на весь процесс. Это то же глобальное состояние, и два клиента не договорятся; передавай аллокатор в контекст.
- Блок освобождён другим аллокатором, чем выделен. Объект запоминает аллокатор при создании и не принимает его снова при каждом вызове.
- Форматирование чисел и разбор строк зависят от локали хост-программы. Библиотека не вызывает `setlocale`; как изолировать разбор от локали, описано в [строках и буферах](06-strings-and-buffers.md).

### Не меняй раскладку публичных структур и закладывай размер в структуру опций

Бинарный интерфейс (ABI) фиксирует раскладку структур, размеры типов, сигнатуры и имена функций в уже собранных клиентах; библиотека, у которой они поменялись, ломает программы без перекомпиляции, часто молча. Простейшая защита: непрозрачный тип (клиент не знает раскладку), а для публичной структуры опций первым полем идёт её размер, и библиотека читает только поля, которые клиент знает.

```c
#include <stddef.h>
#include <stdio.h>

typedef struct {
    size_t size;    /* клиент пишет sizeof(conn_opts) из своего заголовка */
    const char *host;
    int port;
    int timeout_ms; /* добавлено в версии 1.1 */
} conn_opts;

#define HAS(o, f) ((o)->size >= offsetof(conn_opts, f) + sizeof (o)->f)

static int effective_timeout(const conn_opts *o) {
    return HAS(o, timeout_ms) && o->timeout_ms ? o->timeout_ms : 3000;
}

int main(void) {
    conn_opts fresh = {.size = sizeof(conn_opts), .timeout_ms = 500};
    conn_opts old = {.size = offsetof(conn_opts, timeout_ms)}; /* клиент из версии 1.0 */
    printf("%d\n", effective_timeout(&fresh)); /* вывод: 500 */
    printf("%d\n", effective_timeout(&old)); /* вывод: 3000 */
}
```

Старый клиент собран по заголовку без `timeout_ms` и передаёт меньший `size`; новая библиотека поле не читает и берёт умолчание. Поле можно добавлять только в конец. Добавление новой функции ABI не ломает, поэтому интерфейс растёт функциями и полями в конце структур, а не изменением существующего.

#### Подводные камни

- Перестановка, удаление или смена типа поля публичной структуры. Клиент читает старые смещения; любое такое изменение требует новой мажорной версии.
- Структуры по значению в публичных функциях. Раскладка входит в вызов, и добавить поле нельзя; передавай указатель.
- Перечисление без базового типа: его размер определяет реализация, а новое значение ломает клиентские `switch` без `default`. На границе ABI используй перечисление с фиксированным базовым типом или целое с константами.
- Публичные глобальные переменные и `inline`-функции в заголовке. Первые закрепляют адрес и тип, вторые копируются в клиентов, и исправление в библиотеке до них не доходит; оба вида считай частью ABI.
- Изменение смысла функции при той же сигнатуре (другой владелец результата, другие коды ошибок). Бинарно всё совместимо, поведение сломано: это тоже изменение интерфейса.

## Коротко

### Публичный заголовок: версия в пути, extern "C", вариант с va_list

Несовместимые изменения выпускают как новую мажорную версию с другим путём заголовка (`#include <lib-2/lib/x.h>`), чтобы обе версии стояли рядом; если они должны жить в одном процессе, префикс символов тоже меняют (`lib2_`). Заголовок, который включают и из C++, оборачивают в `extern "C" { ... }` под условием `__cplusplus`. Функция с `...` не передаёт аргументы дальше, поэтому рядом пишут вариант с `va_list`, а вариант с `...` делают тонкой обёрткой; атрибут `format` включает проверку строки формата.

```c
#include <stdarg.h>
#include <stddef.h>

#ifdef __cplusplus
extern "C" {
#endif
int msg_vformat(char *dst, size_t cap, const char *fmt, va_list ap);
[[gnu::format(printf, 3, 4)]] int msg_format(char *dst, size_t cap, const char *fmt, ...);
#ifdef __cplusplus
}
#endif
```

### inline: static inline в заголовке или внешнее определение в одном файле

Функцию, которую нужно подставлять из заголовка, пишут `static inline`: каждая единица трансляции получает собственную копию, проблем компоновки нет. Вариант без `static` требует ровно одного внешнего определения в одном `.c` через `extern inline`, иначе при отказе компилятора подставить вызов возникает неразрешённый символ; такая функция не вправе обращаться к `static` функциям и изменяемым `static` объектам (предупреждение `-Wstatic-in-inline` в Clang, `is static but used in inline function` в GCC).

```c
/* clamp.h */
#ifndef CLAMP_H
#define CLAMP_H
inline int clamp(int x, int lo, int hi) { return x < lo ? lo : x > hi ? hi : x; }
#endif
```

```c
/* clamp.c */
#include "clamp.h"

extern inline int clamp(int x, int lo, int hi); /* единственное внешнее определение */
```

### Оборачивай идентификаторы в строгие типы

Две сущности с одинаковым целым представлением (`user_id` и `order_id`) путаются при передаче параметров; обёртка в структуру делает такую путаницу ошибкой компиляции без затрат во время выполнения.

```c
#include <stdint.h>

typedef struct { uint32_t v; } user_id;
typedef struct { uint32_t v; } order_id;
int user_load(user_id id); /* user_load((order_id){7}) не скомпилируется */
```

### constexpr и enum с базовым типом вместо #define

Константу вида `#define MAX_NAME 64` заменяют на `constexpr int MAX_NAME = 64;`: у неё есть тип, область видимости, она видна отладчику и допустима как размер массива. Набор именованных значений описывают `enum` с базовым типом (`enum color : uint8_t { RED, GREEN };`): размер перечисления становится известным и стабильным, что важно для раскладки структур. В директиве `#if` `constexpr`-объект использовать нельзя: там по-прежнему нужен макрос.

```c
#include <stdint.h>

constexpr int MAX_NAME = 64;
enum color : uint8_t { RED, GREEN };
static_assert(sizeof(enum color) == 1);
char name[MAX_NAME];
```

### Имена: не зарезервированные, по роли, без указателя в typedef

Зарезервированы для языка и библиотеки, и пользовательский код их не определяет: имена с ведущим подчёркиванием и заглавной буквой (`_Buf`), с двойным подчёркиванием в начале, с ведущим подчёркиванием в области файла, суффиксы `_t` (типы стандарта и POSIX) и `_s`. Внешние имена `str`, `mem`, `wcs` плюс строчная буква (`strlist`, `memcopy`) отведены под будущие функции библиотеки; `str_len`, `mem_alloc` и тип `str` допустимы. Поэтому типы в книге без `_t`, а публичные имена начинаются с префикса модуля. Имя отвечает на вопрос «зачем это нужно», а не «как устроено» (`retry_limit`, а не `n2`), глаголы одинаковы по всему модулю (`create`/`destroy`, `init`/`clear`, `get`/`peek`/`take`). `typedef` вводят для структур, непрозрачных типов и указателей на функции; указатель в нём (`typedef struct buf *buf_ptr;`) скрывает владение и `const` (`const buf_ptr` неизменяемый указатель, а не данные), поэтому звёздочку оставляют видимой.

### Стиль и условная компиляция

В существующем файле действует его стиль; форматирование закрепляют файлом `.clang-format` и применяют автоматически, чтобы оно не обсуждалось на ревью. Функции-макросы заменяют на `static inline`: у параметров есть типы, аргументы вычисляются один раз. Макрос, нужный одному файлу, убирают через `#undef` в конце использования, а `-Wunused-macros` находит неиспользуемые. Блок под `#ifdef` не проверяется компилятором в выключенной конфигурации и ломается незаметно: если ветка допустима в любой конфигурации, оформляй её обычным `if` над константой, а мёртвую ветку удалит оптимизатор.

```c
#include <stdio.h>

#ifndef CONFIG_TRACE
#define CONFIG_TRACE 0
#endif

void trace(const char *s) { if (CONFIG_TRACE) puts(s); }
```

`#ifdef` оставляют там, где без него нельзя: объявления, которых нет на платформе, и включаемые заголовки.

## Что ещё стоит знать

Clang поддерживает аннотации допустимости нулевого указателя (`_Nonnull`, `_Nullable`) на указателях в сигнатурах: передача нулевой константы в `_Nonnull` параметр даёт предупреждение `-Wnonnull`; GCC 14 этих ключевых слов не принимает, поэтому в общем коде их скрывают за макросом. Версии символов и имя `soname` разделяемой библиотеки задают через опции линкера (`-Wl,--version-script`, `-Wl,-soname`): они позволяют выпускать совместимые версии под одним именем и разрывать совместимость явным изменением `soname`.
